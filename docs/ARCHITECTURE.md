# 架构

新版的目标架构和接口约定。任务卡引用这里的章节；改动这里描述的接口时，必须同步更新本文。

## 1. 目标

- 以复盘为核心的 KataGo 围棋分析工具，桌面端 Windows / macOS / Linux。
- 安装壳小（目标 < 15MB，不含引擎和模型）。
- 引擎层没有共享锁：每个引擎一个 actor，前后台分析不再靠"租约 / 许可"类对象仲裁。
- 与 Java 版并存：棋谱、分析数据、配置可以互通（第 8 节）。

## 4. 关键接口（草案：实现时可以细化，语义不能变）

### 4.1 go-core

- `Point { x: u8, y: u8 }`：左上角原点、零起算；`Color { Black, White }`、`Move { Play(Color, Point), Pass(Color) }`。
- `BoardSize { width: u8, height: u8 }`：2..=25，允许非正方形（KataGo 默认编译只支持到 19，超出由引擎报错）。`BoardSize::new` / `validate` 返回 `BoardSizeError`；局面构造和坐标转换也验证公开字段，不能靠直接构造绕过尺寸限制。
- `Rules { ko: KoRule, allow_multi_stone_suicide: bool, scoring: ScoringRule }`：`KoRule::{Simple, PositionalSuperko, SituationalSuperko}`；`ScoringRule::{Area, Territory}`。这里不计算终局分数。
- `RulePreset::from_name` 接受下表的精确小写名称，未知名称返回 `UnknownRules`；`rules()` 得到上述规则子集，`as_katago_str()` 得到同名 KataGo 规则串。预设身份独立保留，因为日本和韩国规则在本卡建模的字段相同；`Rules::from_name` 只取得规则子集。映射依据 [KataGo rules.cpp](https://github.com/lightvector/KataGo/blob/master/cpp/game/rules.cpp)。

  | 名称 / KataGo 规则串 | 劫 | 允许多子自杀 | 计分方式 |
  |---|---|---|---|
  | chinese | 简单劫 | 否 | 数子 |
  | japanese | 简单劫 | 否 | 数目 |
  | korean | 简单劫 | 否 | 数目 |
  | aga | 情境超级劫 | 否 | 数子 |
  | tromp-taylor | 位置超级劫 | 是 | 数子 |
  | new-zealand | 情境超级劫 | 是 | 数子 |

- `Position::new(size, rules) -> Result<Position, BoardSizeError>` 创建黑先空盘；`with_setup(size, rules, to_play, stones)` 接受 `(Color, Point)` 序列，作为全新的历史起点，不执行提子。越界、重复点、零气块返回 `SetupError`。`stones()` 为左上到右下逐行的只读数组，`stone_at` / `liberties_at` 对空点或越界返回 `None`；后者计算整块的不同气点数。
- `Position::play(mv) -> Result<PlayOutcome, IllegalMove>`：先提对方，再判断己方自杀，最后判断重复。`PlayOutcome.captured` 是对方被提点，`self_captured` 是自杀移除点（含本手新子），均按行排序。被占、自杀、劫、越界返回带原因的 `IllegalMove`，失败不改变棋盘、轮走方、哈希或历史。
- `Position::play_unchecked_ko(mv)` 供 SGF 回放用，只跳过劫检查；仍判越界、被占和自杀，照常提子，并将结果记入历史。两个入口都采用 `Move` 指定的颜色，允许棋谱中连续同色着手，成功后轮走方为该颜色的对方；轮次约束由调用方决定。
- 自杀语义与 KataGo 一致：单子自杀在任何规则下都非法；`allow_multi_stone_suicide` 对应 `multiStoneSuicideLegal`，只控制是否允许移除至少两颗己方棋子（含本手新子），合法多子自杀仍受劫规则限制。六种预设中仅 tromp-taylor 和 new-zealand 开启此项。正常落子和 `play_unchecked_ko` 都执行同样的自杀检查；预设字符串仍原样传递给引擎。
- 简单劫禁止立即回提单子劫；pass 清除此限制。位置超级劫比较盘面，情境超级劫比较盘面加下一轮走方；历史哈希集合包含初始局面和每个成功着手的结果。pass 总是合法，也记入历史；连续 pass 不在本层关闭局面。
- `Position::hash() -> u64`：固定种子生成的 Zobrist（尺寸 + 盘面 + 轮走方），落子和移除棋子以 XOR 增量更新；`recompute_hash()` 从棋盘重算。哈希不含规则和着手历史，不能代替 document 的 `AnalysisKey`。
- 坐标方法：`Point::to_gtp(size)` / `Point::from_gtp(text, size)` 和 `to_sgf` / `from_sgf`；`Move` 提供同名方法，解析时额外传入颜色。19 路 `(15, 3) ⇄ GTP "Q16" ⇄ SGF "pd"`。GTP 跳过 I，按棋盘高度翻转行号，输入不区分大小写，拒绝空白和前导零；SGF 只接受小写坐标。pass 输出为 GTP `pass`、SGF 空值；宽高都 ≤19 时兼容 SGF `tt` 为 pass，更大棋盘按实际点或越界处理。`Point` 不表示 pass，解析 pass 返回 `CoordinateError::PassHasNoPoint`。

### 4.2 sgf

- `parse(bytes: &[u8]) -> Result<Collection, SgfError>`：`Collection { games: Vec<GameTree>, encoding: String, warnings: Vec<Warning> }`。`GameTree { sequence: Vec<Node>, children: Vec<GameTree> }` 保留 SGF 的非空节点序列和有序变化；`Node { properties: Vec<Property> }`、`Property { identifier: String, values: Vec<String> }` 保留属性顺序、重复属性及非空值列表（值可以为空字符串）。
- 编码顺序为 BOM → 合法 UTF-8 → 第一盘根节点的 `CA` → GB18030 兜底。支持 UTF-8 / UTF-16LE / UTF-16BE BOM；有 BOM 的损坏内容直接报错。`CA` 通过 `encoding_rs` 支持 GBK / GB18030、Big5、Shift_JIS、EUC-KR 等明确声明；不进行统计猜测。解码不插入替代字符；声明未知或与实际采用的解码器不一致记 warning。`encoding` 记录所用解码器，带 BOM 时加 `-BOM` 后缀；未声明的 GBK 字节无法与 GB18030 子集区分，统一报告 `GB18030`。整个 collection 使用同一个字节编码。
- 宽松恢复：全小写属性名转大写，FF3 混合大小写长名仅保留大写字母；重复属性保留为独立条目。EOF 缺少树的右括号时补齐。未转义的 `]` 仅在后面不是合法 SGF 边界、且下一个未转义 `]` 位于 `;` / `(` / `)` 之前时作为文本恢复；有歧义时优先采用合法 SGF 结构，不跨节点猜测。每个恢复点记录 `Warning { position, kind }`。
- `SgfError { position, kind }` 是带位置的类型化错误。位置是零起算字节偏移：语法错误和 warning 相对于去 BOM 后的 UTF-8 解码文本，解码错误相对于原始输入。缺失属性值、未闭合值、无节点的树、变化后继续同一序列等不可恢复语法返回错误。变化树最多嵌套 256 层（根为第 1 层），超限返回错误；普通着手序列扁平存储，解析和序列化使用显式栈。
- 属性值仅做 SGF 反转义：反斜杠续行删除，CR / CRLF / LFCR 统一为 LF，其余空白及文本保留；不按 Text / SimpleText 类型裁剪。未知属性（包括 Java 版的 `LZ` 分析属性）同样保留。坐标、贴目、规则的语义解析放在 document 层。
- `serialize(&Collection) -> String`：对合法构造的树输出 UTF-8，正确转义 `]` 和 `\`，换行统一为 LF；不修改传入数据。每盘根节点的第一个 `CA` 原位置写为 `CA[UTF-8]`，去除其余根 `CA`，缺失则追加；非根 `CA` 原样保留。往返树比较仅对根 `CA` 做这一必需的规范化，其余属性、值及变化结构逐项相同；解析后的 `LZ` 文本逐字节一致。

### 4.3 document

- `GameDocument` 是纯同步 arena 树，节点对外只读；`NodeId(u32)` 在单文档生命周期内稳定且永不复用，删除/撤销新建后保留墓碑。通过 `root()`、`current()`、`revision()` 读取状态，`content_revision()` 只在实际内容编辑及撤销/重做时更新到该次 revision，导航、前进到已有子节点和空操作保持不变，`node(id)` 读取父节点、有序子节点、原始 SGF 属性和首个注释。`new()` 创建默认 19 路、中国规则、7.5 目、黑先的空文档。
- `from_sgf(&sgf::GameTree) -> Result<GameDocument, DocError>` 导入一盘；collection 由调用者逐盘选择。序列与变化用显式栈展开，不丢失空节点、属性顺序、重复属性或未知属性。`to_sgf() -> sgf::GameTree` 合并单子节点链为序列，保留节点和变化顺序；UTF-8/CA 规范化继续由 `sgf::serialize` 负责。原始 `KM` 不被归一化值覆写，避免反复导入时二次换算。
- `Command` 包括 `Play(Move)`、`GoTo(NodeId)`、`Step(i32)`、`SetComment(String)`（当前节点）、`DeleteNode(NodeId)`（整棵子树）、`PromoteVariation(NodeId)`（移到同级第一位），以及 P2-01 的 `DeleteBranch(NodeId)`、`PromoteToMain(NodeId)`、`SetGameInfo(GameInfoEdit)`。`Play` 先完整检查轮走方及落子规则，有相同着手的直接子节点则前进，否则追加变化；已有 SGF 子节点也不能绕过新下棋的劫检查。`GoTo` 允许访问非法记录以检查原文；`Step` 正数沿第一个子节点、负数沿父节点，到边界即停。不能删除/提升根。删除当前节点的祖先时焦点退到被删子树的父节点，否则不改焦点。注释修改合并当前节点的全部 `C` 为一个，空字符串删除全部 `C`，保留其他属性。
- `apply(Command)`、`undo()`、`redo()` 返回 `Result<Revision, DocError>`，采用可逆内容修改增量栈。仅新建节点的 `Play`、`SetComment`、`DeleteNode`、`DeleteBranch`、`PromoteVariation`、`PromoteToMain`、`SetGameInfo` 进入撤销栈，并清空 redo；`GoTo`、`Step` 和前进到已有子节点的 `Play` 只更新 `current`，不入撤销栈，也不清空 redo。每次实际改变内容或焦点，包括撤销/重做，都使 `revision: u64` 加 1；无操作不入栈、不增加版本，失败不改变文档。撤销/重做把焦点恢复到该条内容修改记录的修改前/修改后位置，不受后来导航影响。`DocumentSnapshot` 保存活动节点、根和焦点用于渲染/逻辑比较，不包括递增版本、历史栈和墓碑；全撤销/重做恢复全部内容及对应修改记录的焦点，不回拨版本或 ID 分配器，也不恢复操作期间的导航轨迹。
- `DeleteBranch` 遵循 Java `Board.deleteBranch` → `undoToChildOfPreviousWithVariation` → `BoardHistoryNode.findChildOfPreviousWithVariation`：从指定节点向上找到最近一个有多个子节点的父节点，删除通向指定节点的那个子树；主线使用同一规则。如果祖先没有分叉，只删除指定节点及其子树，不把整条无分叉主线清空。根节点按新版命令契约拒绝删除。`PromoteToMain` 沿根到指定节点的每一级交换所选子节点与第一个子节点，复现 Java `LizzieFrame.setAsMain` 反复调用 `Board.setAsMainBranch` 的结果，包括其余兄弟节点的顺序；整条路径作为一项内容编辑撤销/重做。已在主线为无操作，根节点拒绝提升。
- `GameDocument::new_game(NewGameOptions)` 验证宽高 2..=25、有限且绝对值小于棋盘交叉点数的贴目及六种规则预设。0 让子支持矩形；固定让子仅接受 9/13/19 方盘的 2..=9 子，不支持 1 子或其他尺寸的自动摆放。Java `Board.setupFixedHandicap` / `fixedHandicapPoints` 当前只实现 19 路；新版保留其 2–9 子拓扑，9 路映射为零起算星位 2/6、中点 4，13 路映射为 3/9、中点 6，19 路为 3/15、中点 9。黑子写为根 `AB`，`HA` 为让子数，白先，手数和提子数为零；普通新局黑先。双方名字和段位可空。
- `GameInfoEdit` 一次提交 PB/BR/PW/WR、KM、RU、RE、DT、EV，逐字段与当前生效值比较：文本与 `game_info()` 的值比较，贴目与有效 komi 比较，规则与 `rules_preset` 比较。未变化字段的原文、重复属性和多值完整保留；规则未变时 `RU` 不改。逐字段生成新根属性后，再用回放共用的元数据解析计算有效贴目；如果与提交值不同，即使贴目输入未变，也按贴目编辑处理。贴目输入未变且新属性下的有效值仍等于提交值时，`KM`、`KO`、`LZKOMI` 均原样保留。全部相同为无操作，不产生撤销记录、不增加任何 revision，也不改变 modified。确实变化的文本 None 删除相应属性，空串保留显式空值；变化字段的已有同名属性留在原位置并统一更新其值，其余属性及相对顺序原样保留，缺失属性追加。整组实际修改只占一个撤销项。贴目确实变化或新属性使贴目解释偏离提交值时，写入 `KM` 用户原数值，仅在旧来源换算会改变该数值时用私有扩展 `LZKOMI[同一数值]` 标记目单位；仅当标记与首个 `KM` 数值一致时跳过来源换算，仍校验有限性和范围。这样保留野狐 `AP`、`KO` 等原属性，并保证本应用保存再读的有效贴目等于输入，包括会触发旧换算的数值。标记失配时恢复原来源换算；撤销恢复原属性和解释。新局仍显式写入所选贴目和规则，并使用同一贴目标记规则。例如旧野狐 `KM[375]RU[Chinese]` 提交贴目 7.5、规则 japanese 时，写为 `KM[7.5]`，保证即时回放及保存再读的贴目仍是 7.5；一次撤销同时恢复原规则和贴目属性。普通 `KM[6.50]` 仅改规则且解释不变时，保留其原文。第三方 SGF 阅读器可能不认识该扩展。
- `position_at(NodeId) -> Result<GamePosition, DocError>` 按祖先链重算，不维护可失效的局面缓存。`GamePosition` 包含 `board: go_core::Position`（棋盘及轮走方）、完整根起着手 `moves`、累计 `captured_by`（自杀提子归对方）、有效 `rules: RulePreset`、原文 `rules_raw`、`komi`、`handicap`，以及供分析引擎重放的 `initial_stones`、`initial_player`、`analysis_moves`。遇到中途摆子或实际改变轮走方的 `PL` 时，以修改后的棋盘建立新的规则历史和分析起点，清空 `analysis_moves`，完整 `moves` 和提子计数仍保留；`AE` 不算提子。
- P2-06 的 `GamePosition.stone_move_numbers: Vec<Option<usize>>` 与 `stone_node_ids: Vec<Option<NodeId>>` 同棋盘逐行排列，记录当前存活普通着手的根起手数和节点。根着手从 1 起，pass 消耗手数，空节点、摆子和 PL 不增加手数；空点及 AB/AW 摆子均为 None。来源在既有祖先路径回放中随落子写入、随提子和自杀移除，AB/AW/AE 涉及的点清空来源；未涉及的棋子来源保留，PL 不抹去来源。`stone_origin` 直接读取这次回放的数组，不再为来源另回放路径。`preview_variation` 在既有逐手预览循环维护同一数组：原盘幸存子保留来源，新预览子使用从 1 起的 PV 序号（含 pass），没有真实节点，故 node ID 为 None；被提后同点重下使用新序号。这些显示元数据不加入 AnalysisKey。
- SGF 对局信息采用容错读取：根 `SZ` 支持矩形，缺失、不可解析或超出 go-core 尺寸范围时采用 19×19；`HA` 缺失、空或不可解析时采用 0，`HA >= 2` 默认白先。`RU` trim 并转小写后经 go-core 六种预设映射，缺失或不认识则使用 Chinese，原文始终保留。根 `SZ/KM/RU/HA` 和任意节点 `PL` 的重复属性或多值列表，只取第一个属性的第一个值；非根 `SZ/KM/RU/HA` 忽略。`PL` 接受不区分大小写的 B/W，其余值忽略，不阻断回放。任意节点 `AB/AW/AE` 支持单点和矩形压缩范围，以摆子修改而非落子提子处理；摆子和 `PL` 在同节点的 `B/W` 之前应用。着手和摆子的错误仍严格处理：重复/多值着手属性、同节点 `B` 与 `W`、重叠摆子列表、缺气摆子和非法坐标均为节点级错误。
- 贴目先读根 `KM`；缺失、空、解析失败或非有限时尝试根 `KO`（兼容 Cyberoro 等来源，同样只取首值），仍无法使用则采用 7.5。换算后 `abs(komi) >= width * height` 直接采用 7.5。换算保留 Java `SGFParser` 的嵌套条件：根 `AP` 不区分大小写包含 `foxwq` 才认定野狐；野狐 `abs(KM) >= 50` 时先除 100，仅在此分支且原 `RU` 包含 `chinese`、缩放结果在 [-4,4] 时再乘 2。其他棋谱仅 `KM >= 200` 时先除 100，并在此分支内将 [-4,4] 的结果乘 2，随后按 Java 十进制 `.25/.75` 后缀规则乘 2。`KO` 采用同样换算和范围校验。原始贴目属性始终保留，导出不写回回退值。
- `warnings() -> Vec<DocumentWarning>` 返回整棵活动树的文档级诊断，`DocumentWarning { node, property, kind }` 明确指出节点和属性。`WarningKind` 区分重复/多值取首值（`FirstValueUsed`）、解析失败回退（`InvalidValue { fallback }`）、越界回退（`OutOfRange { fallback }`）、未知规则回退（`UnknownRules { fallback }`）、忽略非根信息（`IgnoredNonRoot`）、忽略无效 PL（`IgnoredPlayer`）、PL 大小写规范化（`NormalizedCase`）、使用 KO 贴目（`KomiFromKo`）。普通缺省字段不警告；采用 KO 会警告，非法 KM 回退 KO 时同时记录 KM 原因及 KO 来源。同一属性的多种恢复原因分别记录。诊断按稳定节点 ID 和属性解析顺序返回；读取时重算，不改变 revision、不重复累积，删除子树移除其诊断，撤销恢复诊断；非法着手不妨碍收集其后代或其他分支的元数据诊断。
- 所有 SGF 记录的着手使用 `play_unchecked_ko`，照常提子和检查占用/自杀，允许连续同色。`node_error(id)` 按回放结果标记非法节点及后代，返回带原始出错 `NodeId` 和原因的 `DocError`；`position_at` 对这些节点报错，其他兄弟变化仍可正常回放。导入本身保留非法节点和原属性，不伪造可分析局面。
- 只读展示接口：`game_info()` 读取根节点首个属性的首值，提供 PB/BR/PW/WR、RU、HA、RE、DT、EV 和与回放一致的有效 komi。文本缺失为 None、显式空值保留空串；`rules` 保留 RU 原文，`rules_preset` 由回放共用的根元数据解析返回 go-core 规范名（chinese、japanese、korean、aga、tromp-taylor、new-zealand），缺失或未知 RU 回退 chinese；HA 缺失为 None，存在但无效时沿用 0 的回退。`variation_tree()` 以显式栈按有序深度优先遍历全部活动节点，返回 id、parent、children、move_number、mv、move_error、has_comment；不含墓碑。手数规则与 GraphView 一致，pass 显式表示、空节点 mv 为 None。错误着手仍保留节点，move_error 只说明本节点的着手语法/坐标解码失败，不表示整条路径已通过规则验证；位置合法性仍由 position_at 判断。
- `preview_variation(node, moves)` 在独立 GamePosition 上按完整规则和轮走方逐手执行，首个非法着手立即停止，返回 position、applied_moves 合法前缀及 stop_reason；无效或非法的基准节点直接返回 DocError。`stones` 只包含最终仍在盘上的预览子及其从 1 起算的 PV 序号，pass 消耗序号但没有标记，被提/自杀移除的子不保留标记，提子后重下同点采用新序号。局面同时更新提子数、轮走方、完整着手及分析重放序列。接口仅借用文档，不改焦点、revision、SGF 或撤销/重做栈。
- `GamePosition::analysis_key()` / `AnalysisKey::for_position` 返回 BLAKE3 32 字节稳定哈希。v1 编码固定为前缀 `lizzieyzy-next2:analysis-key:v1\0`，然后 width/height/初始轮走/当前轮走各 u8；摆子数量 u64 小端，按 (y,x,color) 排序后每子 color/x/y；完整 `moves` 与 `analysis_moves` 各为 u64 小端数量后接着手编码（pass 为 0/color，落子为 1/color/x/y）；规则标签 Chinese/Japanese/Korean/Aga/TrompTaylor/NewZealand 为 0..5；贴目为 IEEE-754 f64 位表示的 u64 小端，负零规范为正零。颜色 Black/White 为 0/1。不包含 NodeId、revision、注释、原文规则拼写和提子统计；固定测试向量锁定编码，不能用盘面 Zobrist 或 `DefaultHasher` 替代。

- P2-03 的 `SetSetupStone { point, color: Option<Color> }`、`ClearSetup`、`SetFirstPlayer(Color)` 只编辑当前根快照，根不能含 B/W，也不能有任何子节点，否则返回 `SetupRequiresRoot`。遵循 Java `rootSetupNode` / `setupPlaceStone` / `setupEraseStone`：同色放置、擦空及相同先手均为无操作，异色直接替换，清空保留先手及非摆子根属性。实际棋子编辑把根盘面写为 AB/AW/PL，消除旧 AE；只改先手只更新 PL。均为一项属性编辑，可撤销/重做。Java 允许的零气摆子仍可写入和擦除修复；既有 `position_at` 继续报 `InvalidSetup`，不绕过规则生成可分析局面。
- `GameDocument::to_start_position()` 读取当前合法盘面及轮走方，返回全新单根文档。按照 Java `convertCurrentPositionToStartingPosition` / `materializedRootSnapshotProperties`，保留旧根非摆子属性（包括棋局信息、根评论、标记和未知属性），重建 AB/AW/PL，删除根 B/W 和所有后续着手/分支，手数、提子数归零。非法当前局面返回错误，旧文档保持不变；应用层按 `new_game` 的文档替换处理，不产生跨文档撤销项。
- `SetMarkup { point, kind }` / `ClearMarkup` 只操作当前节点的 TR/SQ/CR/MA/LB，可在不可回放的节点上编辑。`MarkupKind::{Triangle, Square, Circle, Cross, Letter, Number, Erase}` 映射五类 SGF 标记及橡皮擦。遵循 Java `LizzieFrame.tryToMarkup`：同点已有标记时先删除而不替换，即使选择另一种工具；重复导入的同点标记统一删净，橡皮擦点空处为无操作。清空只删除这五类属性，不复制旧 Java `properties.clear()` 或把 AB/AW/AE 当标记的副作用。字母取当前节点 LB 首个 UTF-16 单元最大值与 `@` 的较大者加一，跳过 `[` 到反引号，因此 A/C 后 D、Z 后 a、z 后 `{`；数字按 Java 17 `Integer.parseInt` 的 BMP 十进制字元、ASCII 正负号及 i32 边界读取，再取与 0 的最大值加一，不填空号；分配时只取 LB 首冒号后第一段，显示仍保留完整文字。合法标签中的逗号不复制 Java 内部列表编码的拆分缺陷。超出可表示字符或整数范围返回 `MarkupLabelLimit`，不生成溢出标签。
- `markup_at(NodeId) -> Result<Vec<Markup>, DocError>` 只读根尺寸和指定节点属性，不回放局面或遍历整树；每项含 point、kind、text（形状为 None，LB 保留完整文本）。形状压缩范围展开为各点，数值 LB 分类 Number，其余 LB 为 Letter；非法坐标/损坏标记在视图中跳过但保留原文。未编辑属性及值顺序完整保留，删除范围内单点时仅展开命中的范围，其余标记原样保存。
- `ToggleToPlay` 翻转当前合法局面轮走方，可撤销/重做。Java `Board.changeNextTurn` 对支持指定先手的引擎只改运行时状态，普通着手节点保存时不补 PL；新版采用可持久化的保守表示：当前无 B/W 时更新当前 PL，含 B/W 时追加一个仅含 PL 的空子节点并前进，不改原着手和其他分支，不伪造 pass。这样保持既有“PL 在同节点着手之前应用”的回放语义；空子节点不增加手数，实际轮走变化重建分析起点，`AnalysisKey` 因轮走方改变而不同。

- P2-04 增加 `PlayColored(Move)`、`InsertMove(Move)`、`SwitchStone(Point)`、`DeleteStone(Point)`、`MoveStone { from, to }` 和 `AddVariation(Vec<Move>)`。指定颜色落子只跳过轮走方检查，仍检查占用、提子、自杀和劫；SGF 使用普通 B/W 着手属性，可以连续同色，不以 AB/AW 表示。插入在当前节点与其全部后续分支之间增加一手；改子按当前盘面棋子的来源节点修改颜色、移除着手或替换坐标。每次批量编辑为一项可撤销/重做的内容修改，失败不改变文档。
- Java 行为参照 `LizzieFrame.insertMove`、`Board.editMove`、`LizzieFrame.DraggedReleased` 和 `Board.placeLinkedList`：重接后续着手时，因盘面改变而非法的着手跳过，其后代继续接上；保留变化顺序，未受影响的分支不变。重接时参考 `Board.place` / `BoardHistoryNode.addOrGoto` 复用同色同点的纯着手兄弟；优先复用原来未受影响的兄弟并保留其后续在前，再追加重接的子孙；插入子树内部则首次重放的节点在前。新版保守保留非着手 SGF 属性，带附属属性的节点不合并，不照搬 Java 重建着手链时丢失评论、标记和未知属性或仅按坐标复用异色节点的副作用。新增操作的具体边界及对照用例位于 document 的独立 move-editing 模块。
- `stone_origin(point)` 是只读查询，返回当前仍在盘上的普通着手来源 `StoneOrigin { node, move_number, review_parent }`；空点及仅由摆子生成的棋子没有普通着手来源。追踪当前祖先路径中的提子、重下和摆子，不能把同点更早的已提棋子认作来源。`node` 用于跳到此步；`review_parent` 对应 Java `RightClickMenu2` → `Board.setPressStoneInfo` 的回看起点（落子前的父节点），与直接导航至来源节点不同。查询不编辑、不导航、不消耗历史。
- `AddVariation` 参考 `LizzieFrame.addSuggestionAsBranch` / `BoardRenderer.addSuggestionAsBranch`：首手强制追加独立变化，即使已有相同开头也不合并；通常完成后焦点留在原基准节点。当前为非主干叶节点时，Java 包装入口改走 `playCurrentVariation` / `playVariation` 延长该支，新版同样把焦点放在新串末尾；主干叶节点仍停在基准节点。整串变化一次撤销/重做，恢复对应的前后焦点。新版不为无后续的节点伪造 Java 内部用于定位分支顶端的 dummy pass。显式输入的 pass 正常保留；Java 遇到不可转换的 PV 坐标即停止，新版保守采用整串轮次及规则校验，非法输入整次拒绝，不静默保存部分变化。删除或跳过的节点含非 B/W 属性时保留为空节点承载原属性；纯着手节点才拼接子树至原来的兄弟索引。
- `trial_copy()` 验证当前局面后生成独立文档副本：保留祖先、其他分支、节点 ID 和焦点，裁掉当前节点的所有后续，清空副本 undo/redo。该副本保留原着手路径的规则历史，避免把当前盘面转换成无历史摆子根后绕过劫禁着；可以向前翻手。Java `tryPlay` 临时把当前显示手数置零，新版保持真实路径手数，不维护与棋谱、分析查询不一致的第二套计数；原文档不受副本的导航或编辑影响。

### P3-01 日常棋谱编辑与导出

- `document::BoardTransform::{RotateRight, RotateLeft, FlipHorizontal, FlipVertical}` 通过 `Command::Transform` 对全部活动节点执行一次属性编辑，保留节点 ID、焦点和分支顺序。右转为 `(n-1-y,x)`，左转为 `(y,n-1-x)`，水平翻转为 `(width-1-x,y)`，垂直翻转为 `(x,height-1-y)`，对应 Java `Board.addMoveToList` 的实际方向。左右旋转只接受方盘，矩形旋转返回 `TransformRequiresSquare`；水平和垂直翻转均支持矩形棋盘，遵循 Java `Board.SpinAndMirror` 只限制旋转的行为；整个变换先验证再应用，失败不改变内容或历史，实际变化可一步撤销/重做；空盘等属性完全不变的变换沿既有无操作规则，不增加历史或 modified。
- 着手/pass、AB/AW/AE、点/范围标记、LB 标签、AR/LN 端点以及两组 LZ/LZOP/LZ2/LZOP2 中候选点、PV、ownership 一起变换。LZ 按原 token 替换坐标，保留数值精度、空白和扩展字段；ownership 按行优先重新排列，矩形棋盘同样以 width 为行跨度。非坐标属性保持原文，Java 的 `DD[true]` 保留为非空间 dummy 标志。损坏的已知坐标或不能安全变换的 LZ（含 ownership 长度不等于棋盘面积）整次拒绝，避免在新盘面保留旧坐标。
- `GameDocument::to_clean_sgf(keep_comments, current_branch)` 返回独立导出树，去掉 LZ/LZOP/LZ2/LZOP2、DZ、FIT；关闭 keep_comments 再去掉 C。保留规则、有效贴目扩展 LZKOMI、标记和未知属性。current_branch 从根沿当前节点路径，再沿第一子节点延续至叶子，与 Java selectedBranch 一致；不截在当前手。根也执行清理，不保留 Java raw 根评论/ownership 泄漏。黄金样例在 `crates/document/fixtures/everyday/`，不改原文档及历史。

### 4.4 katago-protocol

- 请求 `AnalysisQuery`：`id`、`moves`、`initialStones`、`initialPlayer`、`rules`、`komi`、`boardXSize`、`boardYSize`、`analyzeTurns`、`maxVisits`、`includeOwnership`、`includePolicy`、`includeMovesOwnership`、`reportDuringSearchEvery`、`firstReportDuringSearchAfter`、`priority`、`priorities`、`overrideSettings`（serde 字段名与 KataGo 一致）。`priorities` 与 `analyzeTurns` 一一对应，录制中按优先级依次返回第 1、2、3、4、0 手。
- `rules` 接受规则名或自定义 JSON 对象；着手为 `(Player, String)`，坐标和合法性留给引擎判断。可选字段用 `Option` 保留是否提供的区别；请求的未知扩展字段保留，以便语义完整地重放录制。
- `Request` 区分 `Analysis` 和 `Action`；动作包含独立的 `id`：`terminate`（另含 `terminateId`）、`terminate_all`、`query_version`。动作确认由 `ActionResponse` 表达；版本回复还含 `version` 和 `git_hash`（下划线拼写）。
- 响应 `AnalysisResponse`：`id`、`turnNumber`、`isDuringSearch`、`moveInfos`、`rootInfo`、可选的 `ownership`、`policy`。候选点与根节点保留录制中的统计字段；所有数值原样读取，黑方视角由引擎配置保证。
- `EngineLine` 分别表示分析结果、`NoResults`、错误、警告、动作确认。错误行允许只有 `error`，`id` 和 `field` 可选；警告同理。排队中被取消的查询以独立的 `NoResultsResponse` 表达：`noResults: true`、`isDuringSearch: false`，没有 `rootInfo` 和 `moveInfos`，不能当成零 visits 的分析结果。
- `parse_line(&str) -> Result<EngineLine, ProtocolError>`：一行一个 JSON；响应中不认识的字段忽略；坏行或缺失必要字段返回类型化错误，不 panic。
- `benchmark::BenchmarkParser` 独立解析官方 benchmark 文本：`push(&[u8])` 接受任意字节分块，按 CR/LF/CRLF 增量分片，单片最多 64 KiB；保留每线程进度和完整的正有限速度行。`finish()` 消费末尾无换行片段并要求明确推荐，拒绝冲突推荐、缺失指标及失败日志；`with_explicit_threads(4)` 可由调用方为固定线程录制显式提供线程数，不从唯一测量行猜推荐（0 表示自动，超过 4096 拒绝）。兼容 Ordered summary、EloDiff 和科学计数法。进入 `Running additional tests of a few other settings` 后，不再发布这些比较试验的线程进度，也不覆盖主测量表或改变线程推荐；另行记录基线、NN 服务线程及批量试验的完整测量和配置组合，并解析 `ADDITIONAL RECOMMENDATION` 中的 `nnMaxBatchSize` 和 `numNNServerThreadsPerModel`，后者支持 Java 的多行建议块。两项建议只附在完成结果，缺少时为 None。NN 服务线程试验被接受后，后续批量试验继承该设置；被拒绝的试验不会改变下一组设置，最终速度按实际采用的组合匹配完整测量，不选择最快或最后一行。
- 两份维护者真实录制均保持原字节：`benchmark-tune-b11-metal.txt` 是 KataGo 1.18.2、B11、Metal 的 `-v 60 -n 3 -s` 格式样本，录制时另一个 KataGo 正在运行；`benchmark-fixed4-b11-metal-batch.txt` 是 M4 Pro、Metal、B11、当前分析配置及相同 override 的 `-t 4 -n 2 -v 30` 样本，包含重复线程行及 batch=2 的额外建议。golden 和 property 测试覆盖两份录制、建议块及任意分块。维护者产品决定与 Java `KataGoBenchmarkParser` / `KataGoRuntimeHelper.parseBenchmarkOutput` 保留主测量显示值的口径不同：采用额外建议后显示对应配置组合的实测速度。因此固定 4 线程样本的主表仍为 15.75 visits/s、15.99 nnEvals/s，完成结果在采用 batch=2 后显示 44.95 visits/s、44.27 nnEvals/s，避免少报最终采用设置的速度；小样本加速比例仍不是正式分析性能保证。

### 4.5 engine-session

```rust
pub fn spawn(transport: TransportSpec, cfg: SessionConfig) -> EngineHandle;

impl EngineHandle { // 可廉价 clone，只持有 channel
    pub async fn submit(&self, req: AnalysisRequest) -> Result<QuerySubscription, SessionError>;
    pub async fn terminate(&self, id: QueryId) -> Result<(), SessionError>;
    pub fn status(&self) -> watch::Receiver<EngineStatus>;
    pub async fn set_auto_check_alive(&self, enabled: bool) -> Result<(), SessionError>;
    pub async fn shutdown(self) -> Result<(), SessionError>;
}
pub enum QueryEvent { Partial(AnalysisResponse), Final(AnalysisResponse), Restarted, Failed(QueryError), Terminated }
pub enum EngineStatus {
    Starting, Ready { version: String }, Restarting { attempt: u32, reason: String },
    Failed { reason: String, stderr_tail: Vec<String> }, Stopped,
}
```

- 一个 tokio 任务独占进程、待完成请求表和状态，外部只能发消息。`AnalysisRequest` 是不含 id 的查询，id 由会话分配。
- `AnalysisRequest` 保留 4.4 中除 `id` 外的全部查询字段；扩展字段不得覆盖协议保留字段（包括 `id` / `action`）。`QuerySubscription::id() -> &str` 是该订阅稳定的取消标识，`recv(&mut self) -> Option<QueryEvent>` 按事件顺序读取，结束后返回 `None`。重发结果中的 wire id 会改变，`terminate` 始终使用订阅的初始 id；对已经结束或未知 id 取消是幂等成功。
- `TransportSpec::LocalProcess { program, args, cwd, env }`。传输层把进程 I/O 变成"发出行 / 收到行 / 退出"三个 channel；以后的 SSH、WebSocket 只需提供同样的三个 channel。
- 本地传输 driver future 由会话 actor 直接轮询，不另起持有进程的任务；参数和环境直接传给子进程，不经过 shell。发出行与收到行各 64 槽，退出为 oneshot；退出报告在 `child.wait()` 和管道排空后产生，包含退出状态及 stderr 尾部。actor 处理退出报告前还会消费已入队的结果，避免遗漏退出前的 Final。关闭先关 stdin，`shutdown_timeout` 后强杀，再等待实际退出；`shutdown()` 成功后状态才为 Stopped。最后一个 handle 被丢弃也会执行清理，status receiver 和查询订阅不会使 actor 永久存活。
- `engine_session::spawn_process(&mut tokio::process::Command)` 为本地分析、版本探测、测速、readboard 和 NVIDIA 探测共用的进程创建入口。仅 Linux 的准确 errno 26（ETXTBSY）重试，最多 8 次，每次间隔 20ms，250ms 后不再开始重试；其他错误和其他平台立即原样返回。使用 Tokio 时间，无锁或自建线程；不改变 argv/env、不通过 shell 重试。引擎和版本探测的原启动总 deadline 包含重试；预算限制重试调度，不能强行中断操作系统的同步 spawn 系统调用。Linux 并行 fork 暂时继承刚写完脚本的写句柄时，等待该子进程 exec 关闭句柄后即可恢复；持久占用仍明确失败，不无限等待。
- QueryId 格式为 `<会话实例号>-<序号>`，重启后旧 id 永不复用。
- 实例号使用 UUID v4，序号由 actor 持有，动作与查询共用递增序列；重发按原始提交序号排列，保留同优先级请求的输入顺序。
- 就绪：启动后发 `query_version`，收到回复才算 Ready；超时（默认 120 秒，首次 GPU 调优可能很慢）进入重启流程。
- 看门狗：`SessionConfig.auto_check_alive` 默认 true；开启且有进行中的请求时，超过 `response_timeout` 没有任何输出，视为挂死并重启。`EngineHandle::set_auto_check_alive` 经 actor 命令动态更新，重新启用重置活性时间；不改变启动握手、写入超时或进程退出处理。
- 重启：指数退避，有次数上限。明显的配置错误（模型或配置文件不存在、启动即退出）直接 Failed，带 stderr 最后 200 行。重启后把进行中的请求用新 id 重发，订阅者收到一次 `Restarted` 后继续收结果。
- `SessionConfig` 默认：`startup_timeout=120s`、`response_timeout=30s`、`write_timeout=5s`、`shutdown_timeout=2s`、`restart_backoff=250ms`、`max_restart_backoff=10s`、`max_restarts=3`、`max_consecutive_bad_lines=3`。超时均可配置为 `(0, 24h]`；重启上限允许 `0..=32`，是整个会话的总预算，Ready 不重置。退避期间和首次启动期间接受排队提交；尚未发给旧进程的请求不会收到 Restarted。启动失败、重启耗尽时保留 Failed 状态供读取，后续提交返回错误，直到 shutdown 或所有 handle 丢弃。
- 背压：订阅者跟不上时只保留最新一个 Partial；Final / Failed 永不丢。
- actor 命令 channel 固定 64 槽、待发队列最多 256 行、同时进行的查询最多 128 个，满载提交返回 `SessionError::Capacity`。每个订阅是一个 watch 槽：一个最新 Partial 加有界可靠事件历史，慢消费者不阻塞 actor；终态在 actor 退出后仍可读。单请求最多 256 个 `analyzeTurns` 项，每个去重手数都保留 Final，仅重发尚未完成的手数并保留对应优先级；可靠历史至多 256 个 Final、32 个 Restarted 和一个终态。取消、重启或失败清除旧 Partial。查询错误只结束对应订阅；未取消查询意外收到 noResults 时报告类型化失败，绝不制造分析值。
- 坏行：记录并计数，不崩溃；连续坏行超过阈值视为协议故障，触发重启。
- 有效协议行重置连续坏行计数；累计坏行数另外用于 tracing 日志。stdout 或 stderr 的任何输出均刷新进行中请求的看门狗；空闲时不运行响应看门狗。tracing 记录请求标识、重发标识、完成／取消耗时和故障原因。
- terminate 的真实行为见 `fixtures/katago/terminate-*.jsonl`：
  - 搜索中取消：先收到确认，再收到该查询的最终结果（`isDuringSearch:false`，带已有的 visits）；
  - 排队中取消：先收到 `{id, turnNumber, isDuringSearch:false, noResults:true}`，之后才收到确认。

  所以不能假设确认先到，也不能假设一定有 `moveInfos`。会话吞掉被取消查询的所有后续输出，订阅者只收到一次 `Terminated`。

### 4.6 analysis（协调器）

- `analysis::spawn(engine: EngineHandle, config: AnalysisConfig) -> Result<(AnalysisHandle, AnalysisSubscription), AnalysisError>` 在 Tokio runtime 内启动一个协调 actor；直接消费 engine-session 的 `QuerySubscription` / `QueryEvent`，不另起进程管理或结果转发任务。
- `AnalysisHandle` 可 clone，提供异步 `focus(Focus)`、`focus_with_cached(Focus, Option<AnalysisResponse>)`、`focus_with_cached_and_resume(Focus, Option<AnalysisResponse>, bool)`、`set_pondering(bool)`、`resume()`、`set_limits(AnalysisLimits)`、`set_live_settings(LiveSettings)` 和 `shutdown(self)`，均返回 `Result<(), AnalysisError>`；成功返回表示命令已经应用。`Focus { revision, node_id, position: GamePosition, key: AnalysisKey }` 的 key 必须匹配 position；相同 revision/node/key 的重复焦点命令幂等；当前请求失败时可重复该命令重试。无效输入不改变已有焦点、查询或状态。`focus_with_cached` 接受调用方按局面 key 和引擎指纹核对的文档保留结果，仅在 node/key 改变或尚无已发布快照时注入缓存；不覆盖更深的 LRU 条目，也不替换同焦点已发布快照。LRU 淘汰后重访仍先发布这份结果并建立显示 visits 下限，再接受追平的实时输出；暂停实时搜索时也可以发布 Cache。
- `AnalysisConfig` 包含 `engine_fingerprint: String`、`cache_capacity: usize`（默认 128，必须大于 0）、`live: LiveSettings` 和 `pondering: bool`（默认开启）。指纹由调用方标识引擎版本、模型和影响评估的配置，在协调器生命周期内固定；更换这些内容必须新建协调器。默认空指纹仅适合单个引擎会话，不表示跨引擎结果可复用。
- `LiveSettings { max_visits: u64, report_interval: Duration, include_ownership: bool, include_policy: bool, query_rules: Option<katago_protocol::Rules>, query_komi: Option<f64> }` 默认分别为 `u32::MAX`、150ms、true、false、None、None；visits 必须大于 0，报告间隔必须在 `(0, 24h]`。达到访问上限后结束该请求，不自动循环提交。实际修改设置清除当前焦点的已发布快照记录和 visits 下限，取消旧请求，再用新设置提交；相同设置是无操作，无效设置不改变已有状态。暂停取消当前请求并清掉未读输出，恢复为同一焦点分配新请求；暂停/恢复保留已发布快照记录及 visits 下限。
- P2-11 的 query_rules/query_komi 是可选请求覆盖，由 app-core 验证并计入不可变引擎分析指纹；`set_live_settings` 拒绝改变覆盖，必须新建协调器避免复用旧缓存。文档 AnalysisKey 继续描述原棋谱，覆盖身份也纳入文档保留结果/清除分析撤销记录及持久缓存的引擎命名空间。存在规则/贴目覆盖时，文件 LZ 仍可按 Saved 来源查看，但不用于满足整盘已分析计算量，需重新计算。
- 请求使用 `GamePosition.analysis_moves` 配合 `initial_stones`、`initial_player` 重放到当前局面；完整 `moves` 不能用于中途摆子或 PL 重置后的请求。规则使用有效预设字符串，贴目使用文档已规范化值，尺寸来自 board；GTP 坐标由 go-core 转换。只分析最后一手，priority 为 0。文档 warning 仍由 `GameDocument::warnings()` 提供，协调器不重复解析元数据或生成 warning。数值依赖 4.7 的引擎 BLACK 配置，响应原样保留，不按轮走方二次转换。
- node_id 或 key 变化：清除未读的旧焦点输出、待节流结果和已发布快照记录 → 用订阅的稳定 id terminate 旧实时请求 → 先推缓存里该 key 的最好结果 → 发新实时请求（`reportDuringSearchEvery` 和 `firstReportDuringSearchAfter` 均使用 report_interval）。关闭或丢弃最后一个 handle 也取消其当前请求，但不关闭共享的 engine-session。
- 仅 revision 变化、node_id/key 不变：不 terminate、不 submit，保留原订阅并更新查询身份；清掉未读的旧 revision 输出，立即用新 revision 重发最近一次已发布快照（如果有，response 和 source 不变）。待节流结果也更新 revision，包括查询已经完成但尚未发布的 Final；此后所有输出均使用新 revision。已发布快照的 visits 下限不变，查询已完成时也不因 revision 变化重新搜索。
- `AnalysisSubscription::recv(&mut self) -> Option<AnalysisSnapshot>` 是取消安全的输出入口。`AnalysisSnapshot { revision, node_id, key, response: AnalysisResponse, source: SnapshotSource, visits_per_second: Option<f64> }` 的 source 区分 Cache / Live；仅发布 revision/node/key 都匹配当前焦点的数据。输出使用有界 watch 邮箱，保留一个未读缓存结果及一个最新实时结果；慢消费者仍先收到缓存，实时中间结果合并，最终结果保留到新命令使其失效。焦点命令成功返回后，旧焦点尚未消费的数据也不可再读到。
- 显示深度：记录当前焦点实际已发布的最新快照及其 visits 下限，缓存快照也计入。实时结果 root visits 小于下限时直接抑制，不进入待节流槽；相等或更大时正常发布。仅收到但尚未发布的结果不抬高该下限。当前查询收到引擎重启事件时清除下限，保留已显示快照直到新结果到达；重启间隙仅 revision 变化仍重发旧快照，但不恢复旧下限。新引擎首份结果即使更浅也正常发布，并重新建立下限，此后照常不倒退。暂停/恢复保留下限，查询追平后才能更新显示；更浅的 Final 也不发布，但请求正常结束。实际改设置或 node_id/key 变化清除快照记录及下限，返回局面后新发布的缓存重新建立下限；缓存始终保留 visits 更多的结果。
- 节流：同一 revision 的正常分析输出至少间隔 50ms，最多 20 次/秒，缓存也占一次；首条立即发布，中间结果合并到最新，符合显示深度条件的最终结果延后到下个允许时刻发布。忙时不补发错过的时钟。仅 revision 变化时的快照重发是新 revision 的首条，立即发送；保留待发结果并把后续正常输出推迟至少 50ms，没有历史快照可重发时则保留原期限。暂停/恢复及改设置不重置节流时钟；node_id/key 变化清掉旧时钟与待发数据。
- 实时搜索速度由当前查询独占的采样器计算：每份通过焦点身份检查的 Partial 在显示深度过滤和节流前，用 `tokio::time::Instant` 记录到达时间与 root visits；仅保留距最新采样不超过 3 秒的数据，按首末 visits 差除以时间差，跨度不足 500ms 为 None。Final 不加入采样，保留最后一次速度；暂停保留已发布快照中的速度。换 node/key、新查询提交（含恢复和修改设置）、Restarted 均从空采样重算；仅 revision 变化和幂等命令保留。visits 回退时保守清空采样，避免负速或下溢。速度不写入 LRU 或文档保留结果，Cache 和整盘结果均为 None。
- 缓存：协调器保留有界内存 LRU（AnalysisKey + 引擎指纹，保留 root visits 最多的结果，相同 visits 更新为后来结果），P2-09 另由 `analysis::persistent_cache::PersistentCache` 提供跨进程 SQLite。`AnalysisConfig.cache_enabled` 默认 true，`set_cache_enabled` 关闭后不读写 LRU、不注入外部缓存。`discard_cached_analysis` 清空内存缓存、显示下限和待发快照，取消旧查询后按原意图继续，保留自动限停原因，不操作数据库。
- SQLite 由独立 Tokio actor 独占，256 槽命令通道串行处理；AppCore 的 Live/整盘结果写入只调用同步 `put`，内部 `try_send` 入队立即返回，不等待 SQLite，也不在 AppCore 序列化整份响应。队列满丢弃本次写入，通过合并通知由缓存 actor 记录拥塞日志，不阻塞应用。actor 按完整键合并待写结果，仅保留一份计算量最高的响应，相同计算量取最新帧；每个键的首次待写开启 1 秒窗口，到期才序列化并落盘。待写最多 128 个键，达到上限先刷新最早的一项。`get` 仍读取数据库，并返回数据库与待写结果中更深的一份，不因读取额外写入分析 payload。
- `flush_position` 刷新该局面所有引擎身份的待写数据，`flush` 刷新全部；普通导航、同节点局面变化、非法局面、换谱、换引擎、测速暂停和分析编辑清空焦点均在丢弃旧焦点前调用相应刷新屏障。关闭缓存、退出和丢弃最后一个句柄也刷新已接受的待写结果；显式清除数据库先移除对应待写项，避免定时写入复活已清除条目。仅生命周期屏障等待落盘，逐帧 Live 写入不等待。
- 每次实际 SQLite 操作通过 `tokio::task::spawn_blocking` 将连接所有权移入、完成后移回，关闭连接同样在 blocking 任务中执行，无共享锁或自建线程。开库惰性进行，关闭开关后自动 get/put 不创建数据库。首次打开、读写或解析失败记录一条 tracing 警告，本次 actor 生命周期禁用持久缓存并丢弃待写结果，返回 miss/忽略写入，不发布引擎故障；下次启动重试，不自动删除损坏数据库。
- 缓存文件为应用数据目录的 `analysis-cache.sqlite3`；桌面壳使用 Tauri `app_data_dir()`，显式 `--config-dir` 同时隔离配置和缓存。无壳调用方通过 `AppConfig.cache_directory` 指定，缺省沿用 settings_directory。`AppConfig.cache_max_bytes` 默认 64 MiB（67108864 字节）；4096 字节页与 `max_page_count` 限制实际数据库文件，FULL auto_vacuum 在淘汰后回收页，MEMORY journal/temp_store 不创建持续增长的磁盘旁车。超过预算按持久递增访问序号淘汰最久未读/更新的条目；单条无法容纳则跳过，容量小于数据库最低开销时降级禁用。
- 持久键由完整 `AnalysisKey` 与版本化引擎缓存指纹组成。局面键包含尺寸、摆子、初始及当前轮走、完整着手/分析重放历史、有效规则和规范化贴目（见 4.3）；引擎键包含现有程序/模型/配置路径、大小、修改时间及额外参数的档案指纹，再纳入保存的 benchmark 推荐和 ownership/policy 请求形状。文件身份沿用元数据，并非内容摘要；原地替换后重新配置/启动取得新身份。缓存保存完整 `AnalysisResponse`，同键计算量不倒退，等 visits 取最新帧，确保定时落盘后的 final/ownership 更新仍可保存；文件 LZ 来源不写入 SQLite。AppCore 在实时焦点提交前选择文档保留与数据库中更深的结果，交现有协调器先发布 Cache、建立显示下限、提交新搜索；校验接受的 Live 和整盘 Final 写回。开始整盘任务时载入已缓存节点，达到目标计算量的节点跳过。速度不持久化。
- `status()` 返回 `watch::Receiver<AnalysisStatus>`，状态为 Idle / Analyzing / Restarting / Limited(LimitReason) / Failed(AnalysisError) / Stopped；Limited 的原因是 Time 或 Playouts。查询故障以类型化错误报告，不伪造分析值；收到 Restarted 清掉待节流的旧 Partial 和 visits 下限，保留已发布快照，继续读取原订阅，由 engine-session 自动重发，协调器不重复提交。
- `analysis::review::ReviewPlan::new(Vec<(NodeId, GamePosition)>, target_visits)` 为调用方提供的待分析节点建立批量计划。每个查询使用 `analyzeTurns`，最多 256 个不同手数，priority 为 -100（实时为 0），包含 ownership；保留搜索中报告以维持会话活性，但仅达到目标 visits 的 Final 计入完成。沿兼容的重放前缀合批，遇到摆子、PL、规则、尺寸或贴目等重放上下文变化时另起查询；空节点可以共享同一手数，一个 Final 映射回多个各自带 AnalysisKey 的节点。超过 256 手分批，过滤完成节点后仍保留原重放手数，不把节点 ID 当手数。
- `ReviewPlan::into_batches()` 返回 `ReviewBatch`，`submit(&EngineHandle)` 得到由 app actor 持有的 `ReviewRun`。`recv()` 取消安全，返回包含 node/key 和完整 `AnalysisResponse` 的结果；`cancel()` 按稳定订阅 ID terminate 并丢弃未读结果。批次顺序提交，重启交由 engine-session 只重发未完成手数，review 层不另行重发；不足目标的 Final、查询失败或未完成就结束均返回明确错误，不伪造完成。这里不保存文档结果、不修改文档，也不另建引擎任务。

### 4.7 app-core 与 Tauri 层

- `app_core::spawn(settings_directory)` / `spawn_with_config(settings_directory, AppConfig)` 异步加载设置，返回可 clone 的 `AppCore` 命令句柄和单消费者 `AppSubscription`。actor 独占 `GameDocument`、engine-session、协调器和设置，64 槽命令通道串行处理，保证"文档修改 → 焦点更新 → 分析"的顺序。`AppConfig` 提供会话超时和协调器参数；引擎指纹及 pondering 由档案/用户设置决定。
- 命令包括 `open_bytes(Vec<u8>)`、`open_path(PathBuf)`、`save(PathBuf)`、`play(Move)`、`step(i32)`、`go_to(u32)`、`apply(document::Command)`、`set_comment(String)`、`delete_node(u32)`、`delete_branch(u32)`、`promote_to_main(u32)`、`new_game(NewGameOptions)`、`set_game_info(GameInfoEdit)`、`recent_files()`、`clear_recent_files()`、`undo()`、`redo()`、`set_pondering(bool)`、`configure_engine(Option<EngineProfile>)`、`settings()`、`shutdown(self)`。成功回复表示命令已应用，不等待分析完成；引擎失败通过事件报告，不撤销已成功的文档操作。所有文档实际变化均向协调器发送 `Focus`，仅 revision 变化也照常发送，由协调器保持查询。
- 对外 revision 是应用生命周期内单调增加的 u64，初始为 0；每次打开和实际文档变化递增，无操作不递增。打开仅取 `sgf::Collection` 的第一盘（`.gib` 路径经 `sgf::parse_gib` 转为普通树，字节入口也接受严格 GIB），并建立新协调器隔离旧文档的节点编号和缓存；解析失败保留原文档。保存使用 `GameDocument::to_sgf_with_analysis` + `sgf::serialize`，同目录临时文件完整写入、flush/sync 后替换目标；保存不改变棋谱内容或 revision，但成功后发布同 revision 的 DocumentChanged，同步文件路径、文件名及未保存状态。
- `AppSubscription::recv()` 取消安全；watch 邮箱为文档、引擎状态、分析、整盘进度、批量分析进度、棋盘同步状态、性能优化进度、实时分析开关状态、打开失败、资源下载进度和应用更新进度各保留一个最新事件，共十一槽，按发布顺序读取，慢消费者的中间事件会合并且不会阻塞命令。同 revision/当前节点的文档刷新后重发邮箱中的原分析帧，保留其来源、候选和速度，让合并后的文档仍先于有效焦点分析到达；不同 revision/节点不回放。文档变化、暂停实时分析、换引擎和关闭清除未读分析；发送分析前再次核对 revision/node/key。导航成功返回后，尚未读取的旧分析也不可再读。关闭或丢弃最后一个句柄会取消实时与整盘查询并等待进程回收，单独保留订阅不延长 actor 生命周期。
- 对外事件：`OpenFailed { path, reason }`（原生路径显示文本和失败原因）、`DocumentChanged { revision, view }`、`AnalysisUpdated(AnalysisView)`、`EngineStatusChanged(EngineStatus)`、`WholeGameProgress(WholeGameProgress)`、`BoardSyncStatusChanged(BoardSyncStatus)`（见 4.11）、`BenchmarkProgress(BenchmarkStatus)`（见 4.12）、`AnalysisStateChanged(AnalysisState)`（见下文 P1-39）。
- 视图 DTO（前端只认这些）：
  - `BoardView`：宽高、每点棋子 `stones`、最后一手（含 pass）、轮走方、手数、黑白提子数。`stones` 与 `AnalysisView.ownership` 均为行优先、从左上角开始，下标 `i` 对应 `PointView { x: i % width, y: i / width }`；`y = 0` 是最上面一行（SGF 的 a 行，19 路为 GTP 第 19 行，矩形棋盘为第 height 行）。数组不翻转、不转置，非正方形棋盘也按 width 计算行跨度。
  - `TreeView`：root/current 节点 ID、含根和空节点的第一子节点主线、当前节点直接子节点数（包含主线），以及整树结构版本 `structure_revision`。`DocumentView.game_info: GameInfoView` 提供 black_name、black_rank、white_name、white_rank、komi、rules、rules_preset、handicap、result、date、event，遵循 document 的根信息语义，不因焦点改变。`DocumentView` 还含当前注释、由 `warnings()` 映射的结构化诊断。非法记录仍可导航，board 为 None，position_error 保留原因；协调器暂停直到回到可分析局面，不伪造棋盘。
  - P2-06 的 `BoardView.stone_move_numbers` / `stone_node_ids` 从上述 GamePosition 数组映射，与 `stones` 同长同序；Rust 始终输出数组，生成 TS 属性可选。`TreeView.branch_start_move_number` 为当前路径首次离开根起第一子主线时的父路径手数加 1，主线上为 null；偏离处是空节点时，表示该支下一手的编号，嵌套分支不重置起点。它在 GraphView 既有显示线计数循环中取得，不新增路径遍历；非法记录仍有分支编号。该字段生成 TS 同样可选，mock 为旧快照补 null，两数组按 stones 长度补 null，保留显式脚本值；变化图预览的 BoardView 使用同样补值规则。
  - 整树采用版本号加按需查询：`AppCore::variation_tree()` / Tauri `variation_tree()` / TS `variationTree()` 返回 `VariationTreeView { revision, comment_revision, root, nodes }`；每个 `VariationNodeView { id, parent, children, move_number, mv, move_error, has_comment }` 可直接绘制，无需在 TS 解析 SGF 或推算颜色。actor 在发布文档时以 O(节点和属性数) 遍历、比较结构并缓存视图，节点增删、子节点换序及其撤销/重做才更新结构版本，导航、注释、分析更新不更新；成功打开棋谱总是更新，解析失败保留旧版本。版本取自该次应用 revision，在应用生命周期内单调增加，初始为 0。DocumentChanged 不携带整树；界面在结构/评论版本变化或首次连接时读取整树，只采用同时匹配最新两版本的回复。结构版本不包含 current，焦点高亮始终来自 DocumentView.tree.current。P2-01 新增独立的 `TreeView.comment_revision`，与查询回复的 `comment_revision` 对应；节点评论的有/无标记变化时更新到当前应用 revision，非空评论改为另一段非空文字无需改标记版本。`has_comment` 表示首个评论非空。导航和分析不改变评论版本；换文档或结构变化由结构版本强制刷新评论标记。界面应在结构版本或评论版本变化时重新读取整树，并同时核对两版本，因此事件合并或重连也不会丢失标记更新。新字段生成 TS 均可选，Rust 始终返回具体值。重连和慢消费者可直接取得最新全量树，不依赖接收过某次增量事件。
  - `AppCore::preview_variation(node_id, moves)` / Tauri `preview_variation(nodeId, moves)` / TS `previewVariation(nodeId, moves)` 返回 `VariationPreviewView { revision, node_id, board, applied_moves, stones, stop_reason }`。输入使用现有 MoveView（Rust 核心为 go-core::Move），通常直接传候选点 pv；可指定任意活动节点而不导航。board 是合法前缀执行后的 BoardView，move_number 是累计对局手数；stones 的 move_number 是从 1 起算的 PV 序号，按合法 PV 顺序列出最终存活的预览子。revision 是执行时的文档版本；界面须同时核对请求时的文档版本、节点和当前悬停请求，丢弃过时回复。命令仅通过 actor 串行读取文档，不发布事件、不修改撤销/重做历史、不调用协调器或触发分析；错误基准节点使命令失败，错误 PV 则返回部分结果及首个错误文字。
  - `DocumentView.graph: GraphView { points, current_index }`：显示线从根经过当前节点，再沿当前节点的第一子节点走到底；包含根、空节点和摆子节点，`current_index` 是当前节点在 `points` 中的零起算下标。每项 `GraphPointView { node_id, move_number, summary }` 的手数与 `BoardView.move_number` 一致：累计根起的着手（含根节点着手和 pass），注释、摆子、PL 不计手也不重置。非法记录仍保留显示线，含 B/W 属性的节点按一手记录计数，不表示着手合法。
  - `AnalysisSummary { winrate, score_lead, visits }` 保留黑方根评估。摘要表由 AppCore actor 独占，以节点 ID 索引；实时结果在 revision/node/key 校验、坐标转换成功并转发 `AnalysisUpdated` 时更新，整盘 Final 在节点/key 校验和坐标转换成功后同样合入。未分析节点为 null，同节点只保留最大 visits，相等时采用后来接受的值；摘要自身不限制分析转发。整盘结果每次合入后发布同一 revision 的 `DocumentChanged`，使图随进度填满，焦点和棋盘不变。成功打开新棋谱清空摘要（P1-38 连续重开同谱可按 key 恢复，见下文），打开失败保留；导航、注释、暂停和删除/撤销保留历史摘要（墓碑不显示，节点 ID 不复用）。引擎产生的摘要与引擎指纹绑定（P2-08 文件来源例外，见第 8 节）：更换档案、原路径文件元数据变化导致指纹改变时清空；停用引擎或新档案无法取得有效指纹时也清空。同指纹重新配置/恢复不清空。清空非空表时立即发布同一 revision 的 DocumentChanged，使界面图数据同步重置，然后才发送新引擎的分析。
  - 图表摘要有效性由 actor 按文档 `content_revision()` 缓存。实际内容编辑、撤销/重做后最多统一校验一次保留结果的 AnalysisKey；导航（Step、GoTo、进入已有子节点的 Play）及分析结果到达后的发布直接查询有效节点集合，不为图上各点重放局面。已通过既有身份/单点校验的实时与整盘结果直接更新该节点的有效性；换谱、换引擎沿原流程清空，重开同谱恢复的匹配结果同步恢复有效性。删除节点的保留结果仍可在撤销后重新校验并恢复显示。`stored_analysis` 和整盘结果接收时原有的单点回放校验不变。
  - `AnalysisView.summary: AnalysisSummary` 表示合并本次接受结果后的该节点最佳摘要，不用于推算候选点的显示下限。P1-23 的文档保留结果独立于 LRU，重访时通过 `focus_with_cached` 发布完整根评估、候选点及 PV，该缓存快照按协调器原有规则建立 visits 下限；引擎重启或修改实时设置仍遵循 4.6 的下限重置规则，此时当前结果可以比最佳摘要浅。前端收到 `DocumentChanged` 时整体替换图数据，收到 `AnalysisUpdated` 时仅按 `node_id` 用事件的 `summary` 覆盖线上对应项，不比较 visits、不自行积攒跨文档摘要或判断换谱。
  - `AnalysisView`：node_id、revision、当前结果的根节点胜率 / 目差 / visits、实时速度 `visits_per_second: Option<f64>`、最佳摘要 summary、候选点、可选所有权数组 `ownership`、is_during_search、Cache/Live/Saved 来源（P2-08 增加 Saved，表示文件内分析）。`CandidateView` 保留显示用 GTP `coordinate`、visits、胜率、目差、先验、顺序，并提供 `point: Option<PointView>`（pass 为 None）与 `pv: Vec<MoveView>`。PV 每手带颜色和格点（或 pass），从当前候选手的轮走方开始逐手交替，pass 也切换颜色。Rust 使用 go-core 已有的 GTP 转换；TS 直接绘制 DTO，不解析坐标或推导围棋颜色。数值和 ownership 从协调器原样保留，不二次翻转。
  - `AnalysisView::from_snapshot(snapshot, size, to_play)` 返回 `Result<AnalysisView, go_core::CoordinateError>`，先用本次根评估初始化 summary，actor 在实际转发时合并历史最佳摘要。actor 在发送 Focus 时保留对应的棋盘尺寸、轮走方，确认输出的 revision/node/key 匹配后才用于转换；非法候选点或 PV 坐标报告错误，不伪造 pass 或格点。9×13 构造响应测试将 `stones`、`ownership`、候选点和 PV 的同一交叉点逐项对齐。

- InstallRuntime 修复等待同一下载 actor 的整组安装终态，失败/取消返回错误；完成后将选中条目的程序指向新目录中相同 pin 的 KataGo，保留模型/配置/参数，并经过原主引擎条目核对及 P2-11 试启动再保存。修复正在使用且路径未变的引擎也会试重启，以重新应用环境；关闭的条目保持关闭。安装期间更换选择或修改条目不会被旧修复覆盖，失败试启动不停止旧会话。成功后返回重新诊断结果。

### P3-04 范围精析与批量队列

- `WholeGameScope` 使用 `type/data` 判别：Line 保持根到当前节点再沿第一子节点到底；Range 的 `first_move/last_move` 是包含两端的实际手数，省略分别取 1 和显示线最后一手，0、越界、倒序或无着手的空范围返回 `WholeGameError::InvalidRange`。实际分析额外包含所选第一手的直接前驱局面：普通棋谱覆盖 `first_move - 1` 到 `last_move` 之后的局面，`first_move=1` 时从根（开局局面）开始，因此第一手也能比较前后胜率和目差、生成评价。区间内同手数的空节点、摆子节点仍计入；第一手前存在空节点时，采用紧邻该手的实际父节点作为基准，起始范围保留根至第一手前的准备节点。普通线路的进度 total 因基准局面增加 1，含空节点时仍按实际捕获节点数计算。AllBranches 使用 document 的有序深度优先节点序列，包含根。三种范围仅生成现有 `ReviewPlan` 的节点列表，进度 total 为节点数；导航不改变捕获的范围。问题手和棋力评估继续读当前显示线，旁支分析不会混入主线报告。
- `force=true` 使用本次任务的已完成节点集合，已有内存、SQLite 和文件 Saved 的计算量不能满足这次任务；每个有效 Final 验证后替换对应旧结果及摘要，即使新计算量更浅。暂停、导航造成的重排和继续保留本轮已完成集合，不重复完成节点；非强制任务继续沿既有深度与 Saved 保护规则。强制任务开始时清除所选局面在 SQLite 中的全部引擎身份缓存及当前协调器 LRU，未重新完成的节点不把旧保留结果注入缓存，防止导航使被替换的更深旧结果复活；这只发生在任务边界，逐帧写入仍不等待 SQLite。
- `Settings.flash_analysis: FlashAnalysisSettings { visits, always_override }` 默认 1、false，旧对象和缺字段补默认。`flash_analysis()` / `set_flash_analysis(settings)` 读写整组设置，计算量为 1..=1,000,000；先原子保存再生效，失败保留旧值，规则仍沿 `engine_settings`。不增加设置版本。
- 主 actor 独占内存批量队列；`start_batch_analysis(BatchOptions { files, visits, scope, force, output })` 将文件按顺序追加到队列并处理 Waiting 项。运行或暂停期间重复 start 返回 `BatchAnalysisRunning`；停止后用空 files 和选项重新开始 Waiting 项，不重做 Completed/Failed。可重复加入同一路径，每项有生命周期内不复用的 u32 ID。队列不写入设置，关闭停止并回收现有分析进程。
- `BatchOutput { suffix, directory }` 的后缀允许 1–64 个字符，拒绝全空白、控制符和跨平台非法文件名字符 `/\<>:"|?*`；不提供 directory 时放在每份输入旁，不自动创建目录。逐盘复用普通导入的 SGF/GIB、编码检测、首盘选择、Saved 导入和文档替换路径，在主窗口展示；批量输入和输出均不更新最近列表。关闭已有棋盘同步后开始批量，批量打开不触发自动速览。
- 每盘由现有整盘调度完成，actor 再复用普通保存的 LZ 导出和同目录临时文件 flush/sync，以禁止覆盖方式发布 `<stem>_<suffix>_<yyyyMMddHHmmss>.sgf`；冲突依次加 `-2`、`-3`。`AppConfig.batch_clock: Arc<dyn BatchClock>` 注入本地时间戳，默认使用 chrono 的本地时区，输出校验为 14 位数字；测试固定时钟。保存成功后当前文档归属输出路径，原谱保持原字节；最后成功打开的一盘留在窗口。引擎规则/贴目覆盖下的 LZ 导出限制仍与普通保存完全一致。
- 文件打开、范围生成、单盘查询或输出保存失败，将该项置 Failed 并继续。引擎消失、Stopped 或 Failed 时整批置 Stopped，reason 保存原因，当前和后续项为 Waiting；引擎内部可恢复的 Restarting 继续沿已有会话重试。每次 actor 轮询至多打开一项，即使一批都是坏文件也可处理控制命令；不另起队列任务、线程或锁。
- `pause_batch_analysis` / `resume_batch_analysis` 暂停及继续当前整盘任务；`stop_batch_analysis` 取消当前查询并把当前项恢复 Waiting。`add_batch_analysis_files`、`remove_batch_analysis_item(id)`、`move_batch_analysis_item(id, BatchMove::{Up,Down,First})` 支持运行中操作，删除和排序只接受 Waiting 项。`clear_batch_analysis` 保留正在处理的当前项（含暂停），清除其他全部项；空闲清空回到 Idle。所有控制命令返回应用后的完整状态。
- `BatchAnalysisStatus { phase, items, current_index, reason }` 的 phase 为 Idle/Running/Paused/Stopped/Completed，current_index 为当前快照的零起算下标；每项 `{ id, path, state }` 的 state 为 Waiting、Running（可空整盘 progress）、Completed（output 路径）、Failed（reason）。`batch_analysis_status()` 读取完整快照，`BatchAnalysisProgress` 使用独立的有界最新槽，沿原有有序 IPC Channel 转发并在重连时回放；TS `subscribeBatchAnalysisProgress` 单独分流，不进入旧 subscribe。
- 运行与暂停期间，打开/系统打开/粘贴/新局/野狐打开、所有棋谱编辑、试下/死活题转换、清分析、普通 save、棋盘同步启动、自动曲线开关与独立整盘控制均返回类型化 `BatchAnalysisRunning`；Step/GoTo、只读展示和纯导出可以使用。野狐下载前和打开下载内容时各校验一次，避免网络期间的竞态；普通 save 保守拒绝以保护批量输入。性能优化启动/重置同样拒绝，避免夺走分析引擎；显式关闭/切换引擎使队列停止并说明原因。更新安装和应用退出也停止队列。
- Tauri 的 `commands/batch_analysis.rs` 与精析设置命令只转发 AppCore，仅授权本地 main。类型由 export-bindings 生成，新设置/视图字段和新 Backend 方法可选，`startWholeGameAnalysis({ visits })` 保持兼容。mock 补默认值，控制与设置写入全部为脚本化 command，设置/状态读取为有默认值的 query，批量进度可脚本回放；没有在 mock 或生产 TS 中实现分析或队列业务。P3-05 再接界面。

- 每种正常结束路径均按 auto_save 保存，即使无结果也保存棋谱。文件名 `yyyy-MM-dd-HHmmss_<黑方>_vs_<白方>.sgf`，限制名字长度并替换跨平台非法字符；时间复用可注入的 `BatchClock` 本地时间戳。目录按需创建，沿既有临时文件 flush/sync 和禁止覆盖的原子发布路径保存；同名递增 `-2` 等后缀。失败通过命令错误及 GameView.error 的 `AutoSave` 报告，已完成阶段和 RE 保持，不伪装成未结束。暂停后换到另一文档的失效会话停止时返回 PositionChanged，不给新文档写旧结果或保存它。
- fake-katago 的 `overrideSettings.maxTime` 纳入已有 `--time-scale` 模拟时间，与 maxVisits 先达到的上限结束。`--play-script PATH` 读取 `{default,turns}`，turns 以查询 turnNumber 为键，整项覆盖 default；每项可指定黑方 winrate/scoreLead、candidates（move、visitShare、winrate、scoreLead、pv）、error、hang、gateFile。门控仅暂停该查询搜索，仍处理版本与取消动作。所有行为验收使用 fake；真实 GPU、桌面人机对局界面及三平台真机操作不由本卡测试替代。

### P3-10 GTP 后端与引擎比赛

- 新的纯同步 `gtp` crate 只依赖工作区内的 go-core；提供带可选数字 ID 的命令编码、标准命令、空行结束的成功/失败多行回复、大小写不敏感的落点/pass/resign 解析。坐标由 go-core 转换；格式错误是类型化错误，黄金样例位于 `crates/gtp/fixtures/`，与 proptest 一起运行。
- `engine_session::gtp::spawn(TransportSpec, GtpSessionConfig)` 复用现有本地进程 driver，独立 actor 独占进程，不改变 JSON 分析会话。握手依次查询 protocol_version/name/version/list_commands，再执行 init_commands；拒绝任何初始化命令即启动失败。一次只有一条命令在途，有界队列满返回 Capacity；握手、写入和回复均有期限，退出/超时不自动重启。`GtpHandle` 提供 ready/command/command_with_timeout/status/console/subscribe/shutdown；单条命令可覆盖回复期限，不影响握手或其他命令。每会话保留最近 2000 行发出、收到和 stderr，进程关闭后仍可读取最后快照。
- `Settings.gtp_engines` 是独立于 KataGo 列表的 `GtpEngineEntry { id, name, program, args, working_dir, init_commands }` 数组，旧设置默认为空。add/update/remove 先验证及原子保存，失败不改内存；使用中的条目拒绝修改。test_gtp_engine 启动新会话、获取身份和命令列表、quit 并回收。程序直接按 argv/cwd 启动，不经过 shell。
- `AiPlayer::Gtp { engine_id, time }` 在同一 P3-09 Session 中运行。GtpTime 支持 PerMove、Byoyomi、Fischer、Absolute、EngineDefault、Custom；Fischer/Absolute 要求 kata-time_settings。Byoyomi 在 genmove 前按会话单调时钟发 time_left，只计算实际 genmove 的用时，不把握手和棋盘同步算入时钟；剩余时间按标准 GTP 向下取整为整数秒发送。已知时间控制的 genmove 回复期限取配置期限与当前可用时间加 5 秒中的较大者，EngineDefault/Custom 无法推导预算，沿用配置期限。启动同步 boardsize/clear_board/komi、可选 kata-set-rules、固定让子已摆点及已有着手；FreeHandicap 从指定 GTP 玩家 place_free_handicap 的合法回复构造根摆子。每回合只补发尚未同步着手，genmove 的结果仍由 document 检查，非法着法不变成 pass。
- 悔棋先尝试 undo，不支持或拒绝时清盘并重放。暂停正在计算的 GTP 时关闭进程，恢复重新启动和重放，避免迟到回复修改棋谱；时钟消耗保留。双方 pass 优先读取 GTP final_score，缺少时尝试现有主 KataGo 数子，再无可用结果则结束为未数子，不写 RE。JSON 分析输出不进入 GTP 控制台。
- MatchSetup 以 A/B 的 MatchPlayer 配置 KataGo 条目及每手参数、WRN/PDA，或 GTP 条目及用时；比赛复用同一对局 Session，双方 AI 只通过 start_match 开始。全局 start 使用 GameStart 表达新局（含尺寸、贴目、让子、规则）或当前局面，另有盘数、换色、手数上限、顺序/随机开局 SGF、随机开局与自动保存。默认 1 盘、交换黑白、自动保存，上限未设置时使用棋盘面积的两倍。开局使用首盘主线末端，当前局面与开局文件互斥。开局 SGF 和当前局面作为完整局面源，保留其尺寸、贴目、规则和摆子，NewBoard 的棋盘选项仅对新盘生效，避免重解释既有着手。标准 GTP 保守只接方盘，自由让子接受 2..9 子且不能同时配置固定让子。
- 比赛中当前主 KataGo 条目复用主会话，其他条目另起分析会话；同一条目只使用一个会话，各方 WRN/PDA 以请求 overrideSettings 提交。比赛运行、暂停和盘间均停止主棋盘实时分析；比赛结束回收额外会话，主会话保留并按原意图恢复实时分析；WRN/PDA 调整从下一次请求生效。比赛过程不写主引擎持久缓存，保存后清除非 Saved 的比赛内存结果，避免带其他引擎或参数的分析被注入主引擎缓存。比赛与人机、批量、试下等模式互斥；浏览仍可用，比赛期间不能改写棋谱或引擎设置。
- 每盘在主棋盘展示。认输、双方 pass、超手数和错误均有终态；后两者不计分，错误保留原因。MatchView/MatchUpdated 提供盘数、执色胜局、和棋、按原因分组的不计分、按开局统计和 A 相对 B 的 Elo/2σ 区间；p 为 0 或 1 时没有估计，区间越过概率边界的一端为 null。pause/resume/stop、set_match_games、match_play_now（仅 KataGo）、match_resign 和 set_match_side_params 通过原 actor 串行应用。stop 不保存当前盘，已完成统计保留。
- 自动保存使用 games_directory 下 `EngineGames/<A>_VS_<B>_<yyyyMMddHHmmss>/` 和 `<序号>_<黑方>_vs_<白方>_<结果>.sgf`；名字做跨平台字符清理，复用原子、不覆写的保存路径。空结果以结束原因标记文件名，不制造 RE；保存错误单独报告。时间和随机种子沿用 AppConfig 的可注入来源。
- `gtp_console(engine_id)` 补读会话日志，`GtpConsoleLine` 推送新增行；AppCore 的有界 2000 行事件队列与既有状态槽按同一发布顺序读取，慢消费者可用 console 补读。gtp_console_send 自动启动未运行引擎；命令先在主 actor 校验并入队，等待回复在独立 future 进行，启动测试同样不阻塞文档命令，测试期间的条目被保留供该测试独占；对局或比赛中拒绝 play/genmove/undo/clear_board/boardsize/komi/fixed_handicap/place_free_handicap/set_free_handicap/loadsgf/quit，包括带数字 ID 和大小写变体。空命令、换行注入及超长行拒绝。其他命令按用户文本传给引擎；控制台不解析围棋业务。
- Tauri `commands/gtp.rs`、`commands/match_game.rs` 仅转发上述 AppCore，权限仅本地 main。MatchUpdated 重连回放最新状态；控制台逐行事件不重连回放，使用日志查询补读。新设置/视图属性与 Backend 方法生成 TS 可选；mock 为新字段补默认值，所有新命令为脚本化 command。`fake-gtp` 独立包按 manifest 构建，支持着法、拒绝、退出、挂起、让子、数子和能力选项；普通测试不使用真实 GTP/KataGo 或 GPU，P3-11 才实现界面。

### P3-12 HumanSL 陪练后端

- 陪练沿用 P3-09 的 `GameSetup` / `Session`，增加 `AiPlayer::HumanSl(HumanSlPlay { rank, pace })`；通过 `start_coach(CoachSetup)` 进入。`CoachSetup` 提供 29 档 `Kyu(20)..Kyu(1)/Dan(1)..Dan(9)`、LiveFeedback/ReviewAfter/LiveAnalysis、Black/White/Random、Natural/Fast/Slow、尺寸、让子、续弈及自动保存。默认 3 段、随机执色、自然节奏、边下边提醒、19 路、无让子。成功开始才保存 `Settings.coach_setup`，`from_current_position` 永不持久化。新设置/视图的生成 TS 字段可选。
- 人类模型是目录 `human-sl` / `purpose=human-style`，固定 b18c384nbt-humanv0.bin.gz 的大小 99066230、SHA-256 `637746e44f0efe00ad1245a50aa9bbf0716efe364c43965ead97bd6835d84ab5`、最低 KataGo 1.15.0。主模型列表、按目录身份/文件名发现的自动配置和官方权重应用入口均排除它。下载沿原资源 actor，显式 `pause_asset_download` 保留本次私有 part，重新 `start_asset_download("human-sl")` 用 HTTP Range 恢复，并重新计算前缀及最终完整文件的 SHA-256；服务器忽略 Range 则安全从头。取消、退出和失败沿 P2-12 清理语义，跨进程不保留断点。`import_humansl_model` 核验源文件和实际复制结果的大小/SHA，不接受仅按大小判断的文件。`humansl_model_status` 返回 Missing、Downloading（含 paused、字节数）、Ready（path）或 Corrupt。
- `EngineProfile.human_model` 为可选路径，参与指纹；可用时启动参数增加 `-human-model`，缺失时普通分析仍可启动，指纹保留缺失身份。开始陪练先核验模型和当前 Ready 版本，低于 1.15.0 返回 `CoachError::UnsupportedVersion`。引擎 SHA 命中目录时使用目录 backend；仅明确识别为 TensorRT（目录身份或程序名含 tensorrt/trt）时返回 `TensorRtUnsupported`，不明后端照常尝试加载。必要时关闭并重启同一主引擎所有者，等待 Ready 期间由已有引擎状态事件报告，不另建陪练引擎。模型未下载/损坏返回类型化错误，普通启动不自动下载。
- 如果本次陪练启动新增了 `human_model`，而重启在 Ready 前失败、停止或超时，就恢复原引擎档案及持久化设置，并按原档案重启主引擎，返回含加载失败原因的 `CoachError::HumanModelLoadFailed { reason }`。原来已经加载人类模型的档案不适用这次恢复，沿原错误路径报告。
- 协议解析可选的顶层 humanPolicy、候选 humanPrior、根 humanWinrate/humanScoreMean/humanScoreStdev；普通分析仍不带 humanSLProfile，自带 analysis.cfg 也没有该配置。陪练请求使用 includePolicy，overrideSettings 指定段位 profile、ignorePreRootHistory=false、rootNumSymmetriesToSample=1 和 7 段以上 0.8/其余 0.5 的 humanSLRootExploreProbWeightless；每个 AI 回合共享 10 秒搜索预算。5 段以下使用 1 visit 的 humanPolicy 温度抽样，非法点剔除重抽；6–9 段先构建最多 12 个高人类概率候选，加 KataGo/policy 首选，再用 allowMoves 搜索、按 Java 分档损失加权，64 visits 起，最多加深四轮且每次不超过 4096。
- 40% 面积以后或对手刚 pass 时另做不含 profile 的 40 visits 检查，执行 pass、避免纯人类 policy 过早 pass、连续低胜率且大幅落后认输规则。所有采样复用原对局 SplitMix64 和 `AppConfig.game_random_seed`；节奏通过 actor 的 Tokio deadline 延后提交已选着手，不占线程、不 sleep 同步。document 在真正落子时再次校验完整规则，非法输出绝不转换为 pass。
- LiveFeedback 和 ReviewAfter 隐藏实时分析；LiveAnalysis 在人的回合照旧实时分析，不评价。评价独立于普通缓存，在用户思考时做 400 visits/1.5 秒 HumanSL 查询；实际候选计算量不足时补查落子后的 200 visits/0.8 秒。内部按落子方计算段位胜率和损失，对外 `CoachMoveRated` 的 winrate_before/after/change 保持黑方视角，并明确 color；points_lost 是该着手的非负损失。这里不能直接照抄 Java 的 `-rootLead`：本应用根评估已经强制 BLACK，只在内部按用户执色转换。
- 恶手评价最多拦住 AI 应手 4 秒；评价确认 Blunder 后持有已选应手，`coach_decision(Retry/ShowBest/Continue)` 分别沿原 take_back 回退并计数、返回推荐点与 human_share、释放应手。提示只在 LiveFeedback、人的回合且浏览最新节点时可用，分析未就绪返回 Reading，首次 Region（左上起 3×3 的零起算 row/column），第二次 Exact；同一 AnalysisKey 仅计一次提示，推荐 pass 无所属区域，直接返回 Exact。
- 0 子新局贴目 7.5，有让子为 0.5 并用户执黑。2–9 子复用 document 的 9/13/19 路固定让子；1 子保守解释为让先（空盘黑先、0.5 目，document 不接受单子固定让子，SGF 不伪造 HA/AB）。续弈只接受盘上已有棋子，保留原有局面、规则、贴目和历史，不重解释为新局。
- 结束仍走原数子、认输、停止、保存路径；Stopped 表示中途结束。`CoachSummary` 汇总结果、原因、总手数、恶手、提示、悔棋及损失最大的三手（有效节点 ID）；`coach_review` 结束会话、聚焦最终局面并恢复普通实时分析。新增 `CoachUpdated`、`CoachMoveRated`、`CoachSummary` 各占一个有界最新事件槽，沿原 IPC Channel 有序发布，`coach_view` 可补读状态，`CoachView.active` 区分结束后待复盘与已退出陪练；不污染普通分析缓存。Tauri `commands/coach.rs` 是本地 main 的薄适配，TS API/mock 只转发或回放脚本；界面归 P3-13。
- fake-katago 接受 -human-model，仅有 humanSLProfile 的请求生成对应人类统计；支持 allowMoves 和按 profiles/turns 指定的人类 policy、候选与根统计。验收使用固定种子、请求日志屏障和 Tokio 暂停时间，不运行真实模型/GPU；真实三平台 HumanSL 加载及交互另由维护者验收。

### P3-16 AI 解说后端

- `commentary` 是纯同步 crate，运行时只依赖 go-core。app-core 从 `stored_analysis` 的同一保留结果表按当前 AnalysisKey 读取实时、整盘、批量和 SGF Saved 分析，不为解说请求新的引擎分析。下一手使用当前节点；范围和整盘固定根起第一子主线，每手使用紧邻父节点的分析；无候选返回 `CommentaryError::NoAnalysis`。设置/PL 重置处保守截断实战后续，不把摆子解释成普通着手。
- 发给 AI 的依据包含棋盘大小、当前轮走方、每块全部棋子和气、根计算量、实际下一手、前三候选及不在前三的实际候选、局部规则重放的实战后续（最多 5 手）与 PV（最多 12 手）、提子、低气块、非法停止和损失。完整棋子库存足以还原当前盘面；不发送对局者姓名、段位、棋谱元信息、文件路径、原用户评论或整份 SGF。用户主动输入的追问和前次回答另作为对话消息发送。内部输入保持黑方评估，只有解说依据明确转换成各局面轮走方视角；UI 原分析数值仍为黑方视角。
- 范围/整盘最多选 5 个、至少相隔 3 手，最后按手数排序；重要性沿 Java 以目差损失、缺失时胜率百分点损失除 10、再缺失时计算量回退。返回 analyzed/selected/omitted，缺候选节点不伪造分析。完整盘面库存不等于坐标白名单：回答只可引用供给的着手、成功重放前缀和与这些点直接关联的棋块棋子，气点和远处无关棋子不能作为凭空建议。
- `Settings.commentary` 保存 base_url、model、remember_key、rank（18k..1k / 1d..9d，默认 5k）、style、terminology、detail、variations 和默认开启的 write_to_comment。版本仍为 1，缺字段补默认；整体校验、规范服务地址、原子保存成功才生效。新设置和 DTO 的生成 TS 字段可选。API key 不属于 Settings，永不写入 settings.json；只有生产 Tauri 启动注入 `SystemKeyStore`，无壳和所有测试用内存/假的 trait 实现。
- 钥匙串账户以规范服务地址区分，macOS 使用 Keychain、Windows 使用凭据管理器、Linux 使用 Secret Service（vendored D-Bus、Rust crypto）。读取惰性进行，不在构造时访问系统。取消记住或更换服务删除旧账户；系统失败保留内存 key、状态 available=false，失败删除在后续显式操作重试。系统交互在 blocking task 内进行，错误不携带 key 或底层自由文本；桌面系统可能要求解锁/授权，CI 只编译真实适配器。
- `AppCore::{start_commentary,stop_commentary,commentary_status,commentary_models,set_commentary_settings,set_commentary_key,clear_commentary_key,commentary_key_status}` 经独立 Tauri `commands/commentary.rs` 薄适配，只授权本地 main。只有一个解说请求在途；HTTP 由独立可取消 future 执行，模型查询也在 AppCore 调用 future 中执行，主 actor 只准备不可变依据、接收状态和写入。HTTP 使用 Bearer、固定 User-Agent、不跟随跳转、15 秒连接及整个操作 5 分钟期限；只在 chat/completions 的 404/405 时尝试 responses 一次，SSE 必须收到各协议明确终态。错误正文限制 240 字符并去除 key/Bearer；不会自动重试 429。
- `CommentaryUpdated` 有请求 ID、Preparing/Generating/Verifying/Completed/Failed/Stopped、delta、完整 text、replacement、选中节点、依据全文、覆盖计数、核对问题和类型化错误。独立最新事件槽与原有有序 IPC 共用；完整文本保证慢消费者合并中间帧不丢最终内容，壳重连回放最新完整快照，`commentary_status` 可补读。更正开始清空草稿并设置 replacement，至多一次；仍有问题时完成展示但不写入。跟随未核对前文的追问也不将该前文带入 SGF。
- 核对成功且保存开启：下一手写捕获的当前节点，范围写范围第一手的节点，整盘写根。经 document 的 `SetComment` 和现有编辑历史写入一次，保持其他用户文字，导航回原浏览节点，整个块可撤销。追问用冻结的同一依据和上次回答，向同一块追加「追问」；写入前再次核对文档内容版本，生成期间编辑则保守拒绝写入，导航可继续。换谱（包括试下/题目/同步重建）取消请求、清前次对话并发布空 Stopped 快照；退出/最后句柄释放取消任务。活动批量、对局、比赛及更新安装时不开始解说。

### 4.8 strength（棋力评估）

- `strength::Estimator::bundled()` 从编译时嵌入的模型 JSON 构造纯同步估计器，无网络、文件 I/O 或异步运行时。`estimate(&[MoveInput])` 返回黑、白、整体 `StrengthReport`；每手输入包括手数、颜色、坐标、前后根评估的损失及落子前按 order 排序的候选点；app-core 先通过 P1-24 每手损失入口检查有效性。候选点的胜率由 app-core 从黑方概率转换为落子方百分点，目差同样转换到落子方；这只是计算差值的内部输入，对外局面分析仍为黑方视角。
- `Sample::from_input` 复现 Java `PlayerStrengthEstimator`：命中候选时优先使用同一父局面首选与实际候选的差值；严格首选、前三、前五按候选列表位置计数，未命中为 999；复杂度按 prior 加权的候选损失计算（排除 order >= 999 的追加候选），无 prior 时回退次选差。损失取非负，复杂度限制到 0..1，难度权重为 `clamp(max(complexity, score_equivalent_loss/4), 0.05, 1)`；无目差时以胜率百分点损失除以 6 换算。未命中候选时按 Java 使用前后根评估差；P1-24 既有问题手采用首选候选到落子后根评估，两者口径分别保留，不修改问题手结果。前后分析缺失、key 不符、非法记录、摆子或轮走重置等均沿用 P1-24 的排除规则。
- Java 的 29 项特征按固定 20 索引输入 XGBoost，各树从根沿 `<` 分支推理，缺失特征走 `default_left`，累加 base score 后限制到 [-1,12]，再应用配套残差校准。模型文件逐字节来自 Java `src/main/resources/models/strength/`；来源、SHA-256 存在 `crates/strength/models/provenance.json`，单元测试核对哈希。`format_rank` 提供 Java 对应的中英文级、段、职业、一线职业与 AI 格式；等级尺计算也位于 Rust。
- `SideReport` 返回原始 29 项特征、校准段位、中英文段位文字 `rank_label_zh/en`、固定预测 sigma、样本、严格首选率、前三/前五率、Java 加权吻合度、平均胜率/目差损失、加权损失、失误率、阶段统计和可信度。阶段按整盘手数分为 1..60、61..160、161 以后；无该阶段样本时，特征用的阶段加权损失和好手率回退整体值，并同时返回零样本数。显示等级使用现有 `MoveRankSettings::classify_losses` 对棋力评估实际采用的损失重新分类；`tier_counts` 只把严格首选放入 Best，其余 Best 归 Good；显示评级好手率仅统计 Best/Good，与按目损失划分的 `good_move_rate` 分别保留。
- 整体不足 6 个有效样本时 `has_enough_data=false`；有少量样本仍保留 Java 的低可信估计。单方样本少于 16 为 Low，至少 16 为 Medium，至少 40 且 70% 有目差为 High。完全没有样本的段位及 sigma 为 null，缺少目差的均值/中位数为 null，避免把缺失当作零损失。`total_moves` / `analyzed_moves` 单独公开覆盖率，不把局部分析声称为整盘完成。
- `AppCore::strength_estimate(bounds: Option<[i32; 2]>)` / Tauri `strength_estimate(bounds?)` / TS `strengthEstimate(bounds?)` 返回 `StrengthEstimateView { revision, report, phases, total_moves, analyzed_moves }`。省略或 null 分界使用默认值，原有整盘 `report` 不受分界影响。读取与图和问题手相同的当前显示线，复用 P1-23 保留结果和 P1-24 有效性检查；不导航、不编辑、不启动分析。app actor 仅缓存不可变模型，每次查询从当前保留结果重算整盘和分阶段报告，因此整盘/实时结果、分支切换、换谱、换引擎后立即反映变化，不维护另一份过期报告缓存。调用方先订阅 `DocumentChanged`、`AnalysisUpdated`、`WholeGameProgress` 再读取，按最新请求序号及 revision 丢弃旧回复（分析更新不增加 revision）。命令仅授权本地 main 窗口；全部 DTO 经 ts-rs 生成，mock 只返回脚本数据；界面和 HumanSL 不属于此接口实现范围。
- `Estimator::estimate_phases(&StrengthReport, bounds, last_move)` 是纯同步查询，返回 `StrengthPhasesReport { bounds, phases: [PhaseEstimate; 3], black, white }`。默认分界为 `[60,150]`，分别表示布局和中盘最后一手；按 Java `StrengthPhases.normalize`，第一界线取 `max(10, first)`，第二界线取 `max(first + 10, second)`，负数、过近、倒序均向上规整，不按棋谱长度截短界线。IPC 只接受两个 i32 整数，长度或类型错误由反序列化拒绝；规整结果使用 u32，极大 i32 输入相加不会溢出。
- 三段固定按布局、中盘、官子排列，`PhaseEstimate { index, first, last, played, black, white, black_ranked, white_ranked }` 的 index 为 0..2，范围端点均包含；last 截到当前显示线实际最后一手，`played = last >= first`，与是否有分析无关。每段每方只筛选原始手数落在范围内的该方样本，调用与整盘相同的 `summarize`，不重新编号；原有 `SideReport.opening/middlegame/endgame` 特征统计仍用 60/160 固定分界。保留完整 SideReport（包括少量样本的低可信估计），但只有该方至少 6 个有效样本且段位有限时 ranked 才为 true，界面只能在 ranked 为 true 时显示该段段位。
- `StrengthPhasesReport.black/white` 分别为 `PhaseExtremes { best, worst, worth_reviewing }`。至少两个阶段 ranked 且最高最低相差 >=0.3 段时，best/worst 返回对应 index，否则均为 null；并列取最早阶段。差值 >=0.6 段时 `worth_reviewing=true`。每次查询回显实际分界，不持久化拖动位置；mock 可脚本返回自定义分界的结果，不在 TypeScript 中重算评估。

### 4.9 野狐、腾讯公开棋谱与在线链接

- `fox-kifu` 不依赖其他工作区 crate，使用 reqwest 的 rustls 后端访问公开 HTTP 接口，不需要账号登录、Cookie 或外部 JAR。`FoxClient::search(&FoxQuery)` 返回 `FoxSearchResult { account, page }`；`FoxQuery::{Nickname(String), Uid(String)}` 在 IPC 中使用 `type/value` 判别，数字昵称不会被自动解释为 UID。UID 只接受 ASCII 数字。
- `FoxAccount { uid, nickname }` 保留账号身份；`FoxPage { games, next_cursor }` 的每项 `FoxGame` 包含对局 id、开始时间、黑白 `FoxPlayer { uid, nickname, rank }`、结果和手数。结果由胜方、胜负方式、可选分值及子/目单位组成，区分中盘、超时、点数和其他胜负；显示文案留给界面本地化。段位沿用 Java 的数值偏移及职业 `P` 规则。
- `FoxClient::list(uid, cursor)` 使用服务端最后一项对局 id 翻页，每页上限 100；不足 100 项（包括空页）表示没有下一页，重复游标报错。`download(game_id)` 先用 okhttp UA 依次 POST 主、备用棋谱 CGI，再回退到 H5 GET；HTTP 错误、非 JSON、非零结果或空棋谱均继续下一接口。
- HTTP 使用独立的 20 秒连接超时、默认 25 秒读取空闲超时；持续收到数据会重置读取期限，慢响应不会因总传输超过 25 秒而失败。每次操作（含重试和退避）另有 3 分钟上限、每份响应最多 4 MiB。只有超时、连接和正文传输错误最多尝试 3 次，重试前依次等待 350/700ms；HTTP 状态、JSON、API 和大小错误不重试。`with_endpoints` 的 Duration 参数仅覆盖读取空闲超时，供本地 HTTP 测试注入。
- 下载成功后删除 BOM 和 SGF 属性值外的反斜杠，再按 Java 的确定性规则选择首个含着手的变化、合并根信息和整理着手为主线。保留所选主线的注释、未知属性和值内转义，不依赖全局棋盘去推测拼接窗口碎片。原始 `KM` 保持不变，贴目解释仍由 document 执行；例如 `AP[foxwq]`、中国规则的 `KM[375]` 打开后是 7.5 目。损坏结构返回类型化错误供接口回退。
- 所有失败返回 `FoxError`；`is_retryable_transport()` 是跨平台的网络重试判定，连接失败、连接/读取超时和正文中断均属于这一类，不依赖系统错误码。保留 `Timeout` 与 `Transport` 诊断区别；reqwest 在连接完成前也检查读取期限，因此短期限下 Windows 的连接拒绝可能表现为 `Timeout`。网络错误的 Display 使用可读文案，底层细节只保留在错误源/Debug 中。确认的无账号响应（101201 且 UID 空或 0）与 HTTP、网络、其他 API 或格式错误分开，未知非零码保守作为 API 错误。
- `AppCore::{fox_search, fox_next_page, fox_open_game, fox_clear_history}` 是壳层唯一入口。调用 future 执行 HTTP，应用 actor 只处理客户端取得、历史持久化和下载完成后的 `open_bytes`，慢网络不会占住文档/设置命令。分页参数显式传入，不共享可覆盖的全局游标；下载后沿用本地 SGF 的打开事务、事件及焦点更新流程，失败保留当前文档。
- 成功取得账号和第一页后，才把 `FoxAccount` 记入 `Settings.fox_history`，按 UID 去重、最近成功完成的搜索在前、最多 10 条；加载设置也规范化历史，清空通过同一原子保存流程持久化。`AppConfig.fox_client` 可注入本地测试端点，默认客户端惰性创建。
- Tauri 的 `commands/fox.rs` 提供 `fox_search(query)`、`fox_next_page(uid, cursor)`、`fox_open_game(gameId)`、`fox_clear_history()`，仅授权本地 main 窗口。`CommandError::Fox(FoxFailure)` 保留可本地化的 `Network`（网络错误）、`Timeout`（网络超时）分类及 HTTP/API 状态码；下载回退耗尽时若包含网络原因，仍返回网络分类（优先 Network，其次 Timeout），纯协议失败才返回 DownloadFailed。IPC 只传类型和数据，不暴露平台错误文本；最终提示由界面本地化。其余错误维持原有应用错误边界。所有野狐 DTO 和错误类型由 Rust 递归生成 TS，前端 backend 与 E2E mock 仅转发或回放命令，不实现网络协议或解析。
- 普通测试使用 `fixtures/fox/` 的真实录制和本地假 HTTP 服务；列表裁为 5 盘，昵称、UID 及 SGF 的 PB/PW 一致脱敏，保留字段类型和业务结果，清理敏感字段。录制日期和接口在测试注释中注明。`fox-recorded-2026-10-30.sgf` 保留录制的 177 手棋谱；此外保留 Java 八手回归片段和 [Leela Zero #2285](https://github.com/leela-zero/leela-zero/issues/2285) 公开发布的 313 手完整野狐棋谱；SGF 样本由独立 oracle 校验。`app-core/tests/fox_live.rs` 的联网验收显式 `#[ignore]`，经生产 AppCore 完成昵称、列表、CGI/H5 下载和打开，报告列表盘数、对局 id、手数和贴目，仅使用临时目录，不把未脱敏网络响应写入仓库。

### 4.10 死活题

- `go_core::tsumego::generate` 是纯同步函数，输入尺寸、行优先棋子数组、当前轮走方和选项，输出完整生成盘面、新增棋子、实际进攻方、轮走方、生成贴目及没有空间放置劫材的颜色。算法以 Java `Tsumego` 为行为参考，角、边、中腹、黑白攻、劫材及距离的输出通过本机执行 Java 原算法产生的 `fixtures/tsumego/` 对照样本验证，不使用引擎或全局状态。
- 选项 `TsumegoOptions { to_play, attacker, ko_threat, wall_distance }` 分别支持 Inherit/Black/White、Auto/Black/White、Both/Attacker/Defender/None 和正整数距离，默认 Inherit/Auto/Both/1。自动进攻方保留当前 Java 的实际计数语义：黑子不少于白子为黑攻，否则白攻；不把它解释成新的几何包围检测。墙线偏移为距离加一，默认距离 1 留一行间隙。缺劫材空间为可显示的警告，仍生成题目；四边均无布墙空间则报错并保留当前文档。
- `AppCore::generate_tsumego(options)` / Tauri `generate_tsumego(options)` / TS `generateTsumego(options)` 将生成盘面建成独立的摆子根节点，与 Java 的 root-only snapshot 一致：手数与提子归零、无最后一手，围墙不表示为普通落子链；后续落子和分析使用现有流程。生成贴目来自算法，轮走方写入 PL。全部四项选项保存在 `Settings.tsumego`，旧设置缺字段时使用默认值；验证与原子持久化失败时不改变当前题目或文档。
- app actor 保存首次生成前的完整原文档（含焦点、变化和撤销/重做栈）。再次生成从保存的原局面重新计算，`exit_tsumego()` / `exitTsumego()` 恢复原文档与焦点；无活动题目时退出幂等。正常导航和落子不退出模式，成功打开其他棋谱清除保存的原文档，打开失败保留它。当前 Java 扁平化后丢失原树，其再次执行的前驱回退无法到达原局面，也没有专用恢复入口；此处保留单根生成行为，并按 P1-32 的明确目标补全恢复语义。
- 生成、替换题目和退出均增加应用 revision、发布 DocumentChanged，并重建分析协调器，隔离不同文档中相同节点 ID 的缓存；原分析记录保守清空后重新计算，取消旧整盘任务，避免把题目分析用于原局面。保持现有 pondering 开关，不额外启动真实 KataGo 或改变用户引擎配置。
- `tsumego_status()` / `tsumegoStatus()` 返回 `TsumegoStatus { revision, active, source_node, options, attacker, ko_warnings }`，用于界面恢复模式、已存选项与警告；调用方先订阅 DocumentChanged 再读取，丢弃旧 revision/旧请求回复。三个命令仅授权本地 main 窗口，DTO 全部由 Rust 生成。TS API 只转发命令，mock 只回放脚本。设置窗口、菜单与快捷键由后续界面实现接入；屏幕抓取不在本卡范围。生成根保留原有效规则，其他对局元信息不继承；如果 Java 算法产生无气摆子，仍由 document 的既有局面校验拒绝，不能绕过规则向引擎发送非法局面。

### 4.11 Windows 棋盘同步（readboard）

- 协议来源为 [qiyi71w/readboard](https://github.com/qiyi71w/readboard/tree/a292eea71caaf0cc2f087d3a7563e35db01684b4) 的 `Program.cs`、`MainForm.WebView.cs`、[LaunchOptions.cs](https://github.com/qiyi71w/readboard/blob/a292eea71caaf0cc2f087d3a7563e35db01684b4/readboard/Core/Models/LaunchOptions.cs)、[OutboundBoardSnapshotEmitter.cs](https://github.com/qiyi71w/readboard/blob/a292eea71caaf0cc2f087d3a7563e35db01684b4/readboard/Core/Protocol/OutboundBoardSnapshotEmitter.cs) 和 `SyncSessionCoordinator*`，以及只读 Java 参考仓库的 `analysis/ReadBoard.java`、`ReadBoardStream.java`、`SyncSnapshotClassifier`、`SyncSnapshotRebuildPolicy`、`SyncSnapshotDiffChecker`、`SyncRemoteContext`。以该上游提交的实际发包源码为准，不将旧 fixture 中没有逗号的简写当成当前协议。
- Windows 壳固定解析 `<resource_dir>/readboard/readboard.exe`，工作目录为其所在目录，不接受来自 IPC 的程序路径，不经过 shell。启动参数逐项为 `yzy`、单个空格、单个空格、单个空格、`0`、`cn` 或 `en`、`-1`；三个空格占位是禁用自动落子的时间/访问数配置，不能丢失参数边界。`0/-1` 选择管道方式。Java 还支持 `1/<port>` 的 TCP 回连方式，新版只实现 stdio，无监听端口。P1-34 负责捆绑 exe 及其运行依赖，本卡不下载、更新或打包识别器。
- 双向 UTF-8、LF/CRLF 分行。helper 发 `ready` 后宿主只发送一次 `version\n` 和 `analysisState running\n` 或 `analysisState paused\n`；收到 `version N` 可识别版本但不发自动更新能力。退出发送 `quit\n` 并关闭 stdin。写入与正常退出各有 2 秒期限，超时强杀后等待实际退出；启动后 15 秒没有 ready 报错。stdout 的部分行取消安全地保留，单行限 8192 字节，stderr 持续排空但不当协议解析，避免日志阻塞进程。
- `start W H [hwnd]` 设置尺寸并清空未完成帧；裸 `start` 保留尺寸（初始 19）。每个 `re=` 行是以逗号分隔的一整行棋盘，恰有 W 项；H 行后 `end` 才提交完整快照。编码 `0=空、1=黑、2=白、3=黑末手、4=白末手`，行优先、左上原点，与 BoardView 相同。`clear` 只丢弃半帧，`forceRebuild` 标记下一完整帧必须重建。尺寸、行列数、码值、多末手、坏元信息均验证，损坏帧不提交，后续 start/clear 可恢复；超长行、非法 UTF-8、意外 EOF 为进程级错误并回收进程。
- 帧元信息包括 `syncPlatform`、`roomToken`、`foxMoveNumber`、`liveTitleMove`、`recordCurrentMove`、`recordTotalMove`、`recordAtEnd`、`recordTitleFingerprint`、`lastMoveSource`，都在 end/clear/start 后清除，不能沿用前帧。可用的野狐手数要求平台 fox、明确 foxMoveNumber，且标题/棋谱手数没有冲突。房间、平台、棋谱身份变化不跨局拼接。`lastMoveSource` 区分真实末手标记与棋子数推断，后者不能决定轮走方。
- `sync` 开始持续同步；完整快照亦进入 Syncing。`stopsync` 回到 Ready，保留工具进程；`endsync` 正常结束工具会话并回收进程。`clearBoard` 清空文档但保持棋盘尺寸。`noponder/resumeponder` 暂停/恢复本次同步的分析，不改保存的设置。未知扩展消息忽略；`play/both/noboth/inboard/notinboard` 等自动落子/浮动棋盘控制不在本卡范围，`pass` 是 helper 的交换轮走按钮而非实际停一手，新版暂不执行，绝不伪造 SGF pass。
- `readboard::Decoder`、`Snapshot`、`Cell`、`RemoteContext` 和 `Command::encode` 都是纯同步类型，只依赖 go-core 与 thiserror；不持有 I/O 或线程。唯一 app-core actor 同时独占 readboard 子进程、解码器、同步状态及 GameDocument，通过 select 接收命令和完整行；无额外文档写入任务、锁或共享可变状态。停止命令、应用关闭、丢弃最后一个 AppCore 句柄都等待进程回收，订阅不会延长会话寿命。相同程序与选项重复开始为幂等；新程序启动失败保留原会话。成功打开另一棋谱会先结束同步，解析失败保留现有棋谱和会话。
- 局面整合先匹配同步末端；可信野狐手数还允许匹配主线已有历史节点。唯一新增且末手标记匹配、合法落子及提子后的全盘与快照完全一致时逐手追加，复用已有直接子节点；无标记仅允许可信野狐手数严格 +1 且仅增加一子的情形。无法接上时，无历史、尺寸/房间变化、明确 forceRebuild 或可信远端手数跳变直接重建；已有历史的其他冲突须连续两份相同快照确认，第一帧保持原文档。重建保留对局信息，以 AB/AW/PL 建立合法摆子根，保存可信远端 MN，不编造未看见的历史着手；零气等非法摆子拒绝且保留原文档。应用 revision 持续递增，重建重置节点命名空间、旧分析缓存及整盘任务。
- `BoardSyncOptions { always_sync, always_goto_last, language }` 默认 true、false、Cn，沿用 Java 两个独立选项。`always_sync` 对应「总是保持棋盘一致」：增量后推进同步末端；关闭它不禁用全盘差异校验、提子核验和冲突重建。Java 当前 `shouldResyncAfterIncrementalSync` 本身不使用该开关。`always_goto_last` 决定新手到来时是否跳离用户正在浏览的历史；默认 false 时恢复浏览节点，重复帧不把视图拉回。同步分析焦点独立指向已接受的远端节点：用户浏览其他节点时结果仅更新该远端节点的保留分析和图，不发可叠到错误盘面的 AnalysisUpdated。开始同步自动分析最新局面，停止恢复保存的 pondering 设置；没有已配置的引擎仍可同步棋谱，不伪造分析结果。
- `AppCore::start_board_sync(program, options)`、`stop_board_sync()`、`board_sync_status()` 返回 `BoardSyncStatus { phase, always_sync, always_goto_last, remote_move_number, error }`。phase 为 Stopped/Starting/Ready/Syncing/Failed；开始回复表示子进程已创建，ready/快照通过后续事件确认。远端手数与重建后本地已知手数独立；`error` 保留类型化 UnsupportedPlatform/MissingExecutable/InvalidOptions/Process/Protocol。缺 exe 在启动命令返回 MissingExecutable，不自动下载。Tauri 三个同名命令为薄适配，仅本地 main 窗口可用；非 Windows 开始命令返回 UnsupportedPlatform。没有 macOS/Linux 识别实现。
- `BoardSyncStatusChanged` 与既有事件共享有序 IPC Channel 和第五个有界最新状态槽，壳层重连回放状态；`subscribeBoardSyncStatus` 从同一连接分流，旧 `subscribe` 的事件类型排除此扩展。TS 的 `startBoardSync`、`stopBoardSync`、`boardSyncStatus` 只传命令，所有 DTO 由 export-bindings 生成；mock 仅回放脚本。菜单、状态展示、语言化错误提示和选项界面由后续界面工作接线，本卡没有修改这些部分。
- `fixtures/readboard/reconstructed-session.txt` 是依据上述固定提交的发包源码构造的回放样例，**不是 Windows 实机录制**；公开上游未提供可直接使用的完整现场 wire dump。golden 测试固定解码结果，property 测试检查往返及任意输入不会 panic。fake-readboard 是独立 std-only Cargo workspace，由测试使用本克隆 target 构建；以同样七个参数启动，收到 version 后回放工作目录 replay.txt，记录收到的命令并在退出前写标记。普通集成测试不依赖 Windows、真实识别器或 GPU；这些结果不能替代 P1-34 的 Windows 安装包与真实客户端验收。

### 4.12 用户手动性能优化（benchmark）

- `AppCore::{start_benchmark, cancel_benchmark, benchmark_status, reset_benchmark}` 均返回 `BenchmarkStatus { phase, progress, measurements, last_result, error }`。phase 为 Idle / Running / Completed / Cancelled / Failed；progress 为当前线程的局面完成数、总数及可空两项速度，measurements 为已完成线程的有效测量行，last_result 只返回当前引擎指纹对应的持久结果；完成后文件指纹变化使已完成状态回到 Idle，不显示旧结果，ChangedFiles 的失败原因仍可读取。开始回复只表示已暂停分析并启动测速；后续通过 `BenchmarkProgress` 事件报告。首次启动、自动配置和加载设置均不触发测速。
- 官方快速参数为当前程序运行 `benchmark -config <当前配置> -model <当前模型> -s -n 4 -v 400 -time 5`。Java `KataGoRuntimeHelper.buildBenchmarkCommand` 使用 6 局面、800 visits；维护者决定将新版工作量降至其三分之一，以缩短优化期间全部分析暂停的时间，同时保留官方线程搜索和追加比较。`-s` 让 KataGo 搜索线程数；`-time` 是推荐所针对的每手思考时间，不是进程时限。Java 按对局思考时间取 5–15 秒，新版没有该设置，采用默认 5 秒。当前配置为分析配置：复用档案参数校验和单次 override 合并，保留非线程设置，用 `numAnalysisThreads=,numSearchThreadsPerAnalysisThread=,numSearchThreads=1` 删除分析别名并提供 benchmark 必需的 GTP 搜索键；强制三个日志项 `logToStderr/logAllGTPCommunication/logSearchInfo=false`。不改写用户配置、模型或档案，也不运行 GTP 会话。
- benchmark 进程直接由 app actor 独占，与分析会话分开。stdout 原始字节交给纯同步解析器，stderr 同时排空；两个诊断尾巴各限 8 KiB，部分读取取消安全。只有成功退出、两管道排空且推荐和指标验证通过才保存；总时限仍为 60 分钟，容纳较慢设备上的线程搜索和官方追加比较。按两份 B11/Metal 真实录制的局面耗时线性外推，M4 Pro 这类设备在新参数下可粗估约 7–15 分钟，实际还受候选线程数、模型初始化、缓存和其他负载影响；这不是新参数实跑结果，也不是倒计时保证。取消、失败和应用关闭都强杀并等待实际回收，`kill_on_drop` 仅作兜底。回收失败保留 Failed 和进程句柄，不恢复分析；后续取消可重试回收。
- 开始时取消待定引擎试启动，记录整盘任务是否 Running，暂停该任务但保留固定分析线和已完成结果，清除未读分析，然后关闭协调器和分析进程并等待退出。临时暂停不改写 `settings.pondering`，同步棋盘的分析意图也不被测速覆写。完成、取消或失败在回收 benchmark 后重建分析会话，按当前有效 pondering 意图和焦点恢复；原来 Running 且仍处于 Paused 的整盘任务才继续，跳过已完成节点，原来 Paused 的保持暂停。测速期间用户主动暂停或取消整盘任务优先，不会被自动恢复；换谱、死活题或同步重建造成任务失效时也不恢复旧任务。应用关闭只回收，不重启分析。
- 测速期间重复开始、恢复默认、修改 pondering、配置或试启动引擎、开始或继续整盘分析返回 `BenchmarkError::Busy`。读取状态、文档浏览编辑、整盘暂停/取消和棋盘同步仍可处理；由于分析会话已关闭且有效 pondering 被抑制，不会另起分析争用计算。没有档案返回 NoEngine；进程、解析及保存失败带原因，测速结束前引擎文件指纹变化返回 ChangedFiles，失败和取消不覆盖已存测速结果。
- 结果按原档案的 `EngineProfile::fingerprint()` 存入 `settings.benchmarks`，保存前再次核对指纹并原子写入设置。`BenchmarkResult` 含 engine_fingerprint、recommended_threads、visits_per_second、nn_evals_per_second、measured_at_unix_ms、canonical_model_name，以及可选 nn_max_batch_size、num_nn_server_threads_per_model；未知规范模型名为 null，不伪造识别结果。推荐线程只由官方推荐决定，不自行选择最快行；按维护者追加要求接纳官方 `ADDITIONAL RECOMMENDATION` 的两项设置，不开展独立 GPU/ANE 拓扑或批量搜索。visits/s 是实际搜索访问速度，nnEvals/s 是网络评估速度。没有采用追加建议时，两项取主测量推荐行；采用任一追加建议时，取实际采用的完整配置组合对应的追加测量行。最终两项建议字段仍保留官方建议，显示速度则结合用户显式 CLI override 的实际优先级选择；若只有部分建议实际采用且缺少该子组合的完整测量，明确失败，不保存或展示另一组合的速度。 既有持久记录不包含追加测试原始行，读取时保留原记录，不猜测换算；手动重新优化后保存新口径的速度。
- 推荐 N 通过单次 override 的 `numSearchThreads=,numSearchThreadsPerAnalysisThread=N` 应用于分析启动：N 表示单局面搜索线程数，既有 `numAnalysisThreads=2` 并发局面槽和 BLACK 视角保持。两个可选建议通过同一 override 的 `nnMaxBatchSize`、`numNNServerThreadsPerModel` 应用；沿用 Java 的受管理设置语义，档案 `extra_args` 显式提供同名 CLI override 时保留用户值，否则建议可覆盖配置文件中的值（包括原来的 nnMaxBatchSize=64）。实际采用的判断读取合并后的 CLI 最后赋值：与建议相同仍视为采用，不同则该项不采用；两项均未采用时保留主测量速度。测速结果不写入原档案参数、不改变缓存指纹，因此同指纹重启保留文档分析和整盘已完成结果。Completed 表示测速验证、保存成功且已发起分析重启，不表示新分析进程已 Ready；就绪或重启失败继续由 EngineStatusChanged 报告。恢复默认成功删除当前指纹的整份测速结果后，取消仍携带旧参数的待定引擎试启动；推荐线程及两项额外托管 override 一并撤销，按同样暂停/恢复规则重启，重新使用原配置和档案 override；没有结果时不额外重启。
- Tauri 的 `commands/benchmark.rs` 仅转发四个同名命令，权限只授予本地 main。DTO 由 ts-rs 生成；TS `api/benchmark.ts` 只封装命令，`subscribeBenchmarkProgress` 与其他领域共享有序 Channel 和 unsubscribe，旧 `subscribe` 排除该扩展事件。调用方先订阅再读取 benchmarkStatus。E2E mock 提供 `benchmarkDemoEvents/benchmarkDemoScript` 的进度、完成、失败、取消和恢复默认脚本，示例推荐故意不同于最高 visits/s；这些是界面开发示意数据，不是硬件实测。性能优化窗口、菜单和本地化接线由后续界面工作完成。

- `updates::UpdateHandle` 为独立 Tokio actor 的句柄，壳层在创建 AppCore 后一次性 `attach_updates`。actor 独占官方插件后端、选中版本和已验证安装字节，无锁、自建线程或用户可指定的下载/安装路径。AppCore 的 `check_update` 返回 `UpdateCheck { available, version, notes, published_at }`；`download_update` 立即回复开始状态，`cancel_update_download` 丢弃 HTTP future 和内存数据后回复；`install_update` 只接受已下载且校验通过的包。失败/取消后显式重试从零下载，不假装断点续传。下载期间重复下载幂等，检查和安装返回 Busy；重新检查清掉旧包，即使新清单不可用，也不能安装上次的旧包。
- 壳使用官方 `tauri-plugin-updater`，固定 `https://github.com/wimi321/lizzieyzy-next-v2/releases/latest/download/latest.json`。正式公钥只从编译时环境变量 `LIZZIE_UPDATER_PUBKEY` 通过 `option_env!` 嵌入；其值为 Tauri 生成的 `.pub` 文件中的完整 base64 公钥文本（不是文件路径或私钥），P2-15 在打包构建前注入，变更公钥须重新构建。`tauri.conf.json` 的 `pubkey` 保持空串，仅满足官方配置的必需字段要求；Rust 注册插件时显式传入构建公钥，不读取运行时环境、不回退到配置或内置公钥。缺失或全空白时不注册 updater、不创建更新后端，检查/下载/安装通过 IPC 返回类型化 `UpdateSigningNotConfigured`，供界面本地化说明；不发 HTTP 请求、不启动安装器。上游测试公钥仅存在于 `#[cfg(test)]` 测试向量及注入的测试配置中，生产构建不含测试公钥，仓库不包含私钥。每个平台条目除官方 version/url/signature 字段外必须有 64 位十六进制 `sha256`，下载后核对 SHA-256；官方插件在下载和安装入口都验证 minisign 签名，`requireSignedVersion=true` 要求签名可信注释绑定清单版本（正式签名使用 `tauri signer sign --app-version <version>`）。安装 URL 只接受 HTTPS，HTTP 只在编译测试中的 loopback fixture 开启。客户端连接/读取空闲限制分别 20/30 秒，总请求限制 30 秒，不自动紧密重试。插件整包缓冲，应用限制包大小为 1 GiB。
- 安装采用官方 Windows 安装器、macOS app 替换及 Linux AppImage/deb 路径（按已安装 bundle 类型选择）。进入安装器前主 actor 停止候选进程、资源下载、测速、同步和分析，刷新缓存及日志；不删除或覆写设置、棋谱和缓存目录。安装提交期间拒绝新的修改命令，状态查询与关闭仍可用；调用方断开也会由独立 Tokio future 完成安装或恢复，失败进度在恢复完成后才发布。安装失败恢复原设置的分析引擎；成功后 Windows 插件自行退出，其他平台由命令层在 updater actor 回复后请求重启，避免退出处理等待自身。真实安装包/系统重启仍属平台发布验收，普通测试从不运行真实安装器。
- `automatic_update_check() -> Option<UpdateCheck>` 是供 P2-16 界面启动后调用一次的入口；Tauri 壳只初始化更新后端，不另行抢先检查或消耗 claim。AppCore 先确认更新后端可用：未配置构建公钥直接返回 null，不写检查时间、不联网；已配置时调用 `claim_daily_update_check(now_unix_ms)`，由主 actor 检查开关和时间窗口，并在联网前原子保存 claim。开关关闭或 claim 返回 false 时返回 null；检查仅在发现新版本时返回与手动 `check_update` 相同的 DTO，没有新版本返回 null。时间读取、claim 保存、联网和清单解析等失败只记一条 tracing 日志并返回 null，不向界面传播错误；已保存的 claim 不回滚，失败当日也不重试。沿用 24 小时窗口，时钟回拨时保守跳过，并发调用仅一个取得 claim。手动检查不受窗口限制，应用关闭可以取消等待中的检查。自动检查不暂停分析、不下载/安装、不弹窗；界面启动接线归 P2-16，本卡不在 API 导入或订阅时暗中触发检查。
- `UpdateDownloadProgress(UpdateDownloadStatus)` 带阶段、已收/总字节、版本及错误，进入独立有界最新槽；AppSubscription 共十一槽，壳重连回放新增状态，仍通过同一个有序 IPC Channel。DTO 全部字段与 Backend 新方法可选，旧 subscribe 排除此事件，新增 subscribeUpdateDownloadProgress 单独分流。mock 手动更新命令是脚本化 command，`automaticUpdateCheck?(): Promise<UpdateCheck | null>` 使用默认返回 null 的 query，脚本可覆盖且缺省调用不消耗其他命令；进度可脚本化。设置缺省值按非枚举属性补入，保持旧界面构造及序列化对象的内容。
- `support::SupportHandle` 是独立 Tokio actor，生产壳通过其 tracing Layer 安装全局 subscriber，无壳测试使用局部 dispatcher。默认 INFO，`start_full_log` 开 TRACE 30 分钟，重复启动续期，`stop_full_log` 可提前关闭；Tokio deadline 到时恢复 INFO，`full_log_status` 返回 enabled/remaining_seconds。512 槽非阻塞日志通道拥塞时丢弃新记录，不阻塞分析；单条最多 16 KiB。日志目录按需创建于应用数据目录 `logs/`（显式 --config-dir 时一并隔离），滚动保留 `app.log` 及三个旧文件，每个最多 1 MiB；应用退出刷新。
- `export_diagnostics` 在主 actor 外读取 P2-12 引擎诊断，和设置快照、版本及系统 OS/architecture/family 一起交日志 actor，刷新后以 blocking task 原子生成 `diagnostics/diagnostics-*.zip`，回复完整路径。ZIP 只含 settings.json、engine.json、system.json 及上述日志白名单，不扫描用户目录、不读取环境变量、不将棋谱或模型内容加入包。脱敏类别参照 Java ExportSanitizer、PersistenceSanitizer、SyncDiagnosticsExportSanitizer、ConfigExportProjection：账号/昵称/UID、凭证/密码/token/cookie/authorization/API key/machine key、文件及目录路径（含用户名）、URL、引擎参数、房间/会话标识、SGF/着手内容；保守地删除含敏感数据的整条自由文本，递归脱敏 JSON 键和值，识别百分号及 JSON 转义，异常嵌套脱敏失败关闭。日志落盘前和诊断导出时均执行脱敏。拒绝日志/导出目录及日志文件符号链接，不打包任意文件。
- `log_directory()` 只读返回日志绝对目录，不创建目录或日志；support 启动时固定应用数据根的绝对路径，相对 `--config-dir` 下导出的诊断包也返回绝对路径。`reveal_in_folder(path)` 先由 AppCore 解析目标和实际数据根的 `..`、符号链接，再按路径组件检查包含关系，仅将数据根内已存在的普通文件或目录交给平台调用（包含根目录自身）；不使用配置目录替代独立的数据目录。相对路径及越界路径返回类型化 `RevealOutsideDataDirectory`，缺失、不可解析或平台失败返回 `RevealUnavailable`，拒绝时不调用文件管理器。壳仅使用官方 `tauri-plugin-opener` 的原生函数：Windows/macOS 定位选中，Linux 优先定位，失败后打开文件所在目录或目标目录本身；不通过 shell 拼接命令。不开启插件的通用 IPC 能力，只给本地 main 授予这两个应用命令。新 TS 方法可选，mock 只回放脚本，测试注入假的平台调用方，不打开真实窗口。尚未产生日志时查询仍返回预期目录，显示该未创建目录会明确报不可用。

### fake-katago 测试进程约定

- 启动形状为 `fake-katago analysis -config FILE -model FILE`；接受路径参数及单次 `-override-config KEY=VALUE[,KEY=VALUE…]`；支持的命令行参数重复出现时以退出码 2 报 `Argument already set`（即使值相同也拒绝），不读取模型或配置，也不调用真实 KataGo。输出明确标识版本为 `1.16.5-fake`。
- `fake-katago benchmark` 接受官方 `-s/-n/-v/-time` 参数，默认逐字节回放上述 Metal/B11 录制，不执行搜索或 GPU 运算。`--benchmark-replay PATH` 选择其他样例，`--benchmark-duration-ms N` 控制总回放时长，`--benchmark-gate-file PATH` 在首个进度片段后等待外部文件，用于确定性取消测试；`--benchmark-fail` 注入 stderr 失败并以 1 退出，`--benchmark-pid-file PATH` 记录进程 ID。analysis 模式接受但忽略这些 benchmark 控制项；`--launch-log PATH` 为两种模式追加实际 argv JSON，测试核验重启后的线程 override。模拟数据不因 visits/局面参数重新计算。
- 单个调度器管理排队与运行中的搜索；并发位置数默认 1，`-override-config` 中的 numAnalysisThreads 可覆盖默认值，显式 `--threads` 为测试覆盖且不受参数顺序影响。优先级高的先开始，相同优先级按输入顺序；已开始的搜索不会被抢占。stdin 关闭后排空正常搜索再退出。`--request-log PATH` 可追加实际收到的协议行，供行为测试核对批量手数、优先级、terminate 及恢复时不重复完成节点；不用于生产引擎。
- 同一请求的 `analyzeTurns` 按手数去重、递增入队，重复手数采用最后一个对应优先级；`priority` 与 `priorities` 不得同时提供。只有 `firstReportDuringSearchAfter` 时仍输出一次首次中间报告。未指定初始玩家且无历史时，超过一颗初始黑子、没有白子则默认轮白，其余默认轮黑。
- 候选点及评估由棋盘尺寸、初始摆子、着手序列和手数的固定哈希生成，与请求 id 无关。默认 `maxVisits=100`、`--visits-per-sec=1000`；visits 随模拟时间增长，最终结果达到上限，取消则保留已有 visits。默认评估和 ownership 均为黑方视角；`--default-perspective-to-play` 模拟缺少视角配置时的轮走方视角。显式 `reportAnalysisWinratesAs=BLACK/WHITE/SIDETOMOVE` override 优先于该默认标志；在同一份逗号列表内，同一键重复赋值最后一个生效。除视角和 numAnalysisThreads 外，其它配置键仅接受而不模拟。
- `--time-scale` 表示每个真实秒经过多少模拟秒（默认 1，2 表示两倍速）；搜索、报告间隔、`--startup-delay-ms` 和 `--crash-after-ms` 都使用模拟时间。启动与定时崩溃从进程调度器初始化开始计时。
- `--crash-after-queries N` / `--hang-after-queries N` 在接受第 N 个有效分析请求时触发，动作不计数，0 表示启动即触发。崩溃退出码为 1；挂起后连版本回复、取消确认也不再输出，直到进程被终止或定时崩溃触发。
- `--fault-once-file PATH` 为查询崩溃／挂起、`--crash-after-ms` 定时崩溃和 `--fail-startup` 启动失败共用一个跨重启的一次性标记：仅在首次实际触发故障时原子创建文件，已有普通文件则跳过故障，文件错误明确报错。首次进程到达定时崩溃期限时创建标记并退出，重启后的进程跳过该故障并清除已到期的 deadline，避免忙循环；启动失败同样只触发一次。正常启动及尚未触发的故障不消耗标记。测试使用独立临时路径并负责清理。
- `--startup-gate-file PATH` 在外部创建普通文件后才允许处理 stdin（也须满足启动延迟），用于确保请求在 Ready 前全部入队。假引擎不创建或删除该文件；等待期间定时崩溃仍生效。
- `--fail-startup` 未被一次性标记跳过时，立即向 stderr 写入“模型找不到”并以退出码 1 退出；`--garbage-every N` 在每 N 条正常 stdout 协议行后额外插入一行坏数据，故意用于测试会话的坏行处理。
- 取消顺序遵循录制：排队结果先 `noResults`，然后动作确认，最后是运行中查询的最终结果；`terminate_all` 同时取消所有排队与运行中的位置。
- 假引擎检查坐标、已有棋子、提子、自杀和简单劫；不作为完整规则裁判，不模拟超级劫、真实搜索、模型设置或对称剪枝。录制对照比较公共字段与状态顺序；重复中间采样数量和条件性 `isSymmetryOf` 不要求与 GPU 搜索逐项相同。
- 测试库函数 `fake_katago::binary_path() -> Result<PathBuf, BinaryPathError>` 首次调用执行 `cargo build -p fake-katago --bin fake-katago --locked`，从 Cargo JSON 消息取得可执行文件路径，尊重目标目录及平台后缀。同一进程用互斥锁串行初始化，其他调用者等待后直接复用成功缓存的路径，避免并发构建删除并重新链接可执行文件的竞争；构建失败不缓存，后续调用可重试。仅供运行时测试调用，不用于构建脚本或产品代码。
- 棋力阶段集成测试只分析 36 手、每局面 1 visit，关闭持久缓存和自动速览；准备文件/构建假引擎在安全期限外，先等待 Ready 再等待整盘完成事件，期限仍为 5 秒。168 手默认 60/150 及自定义阶段分组的完整覆盖由同步 actor 测试注入有效结果验证，不把大批搜索、磁盘持久化或进程构建速度当成阶段逻辑断言。ETXTBSY 重试使用虚拟时间测试错误分类、次数/时间上限及取消；Linux 另保留真实持写句柄复现和 8 路 × 2 次并发执行测试，macOS 不声称完成 Linux 内核验证。
- 会话测试的非目标运行超时大于外层 5 秒安全期限，避免慢机器误走故障路径。看门狗测试先观察一次性挂起标记，再推进 Tokio 虚拟时间；推进后立即恢复实时时钟，正常重放使用宽松超时。启动队列由外部文件释放，FIFO 和优先级通过长搜索占用单个搜索槽、逐次取消来验证，不依赖消费者被调度的先后顺序。

## 8. 与 Java 版的兼容

- P2-08 由纯同步 `document::lz` 解析/写入 Java `SGFParser` / `SgfAnalysisPayloadWriter` 的 LZ 格式。`saved_analysis(NodeId)` 读取最后一个有效主槽（LZ/LZOP），`SavedAnalysis` / `SavedCandidate` 保留根胜率、rootVisits、目差、标准差、PDA、WRN、候选顺序、prior、edgeVisits、PV/pvVisits 和 ownership。header 的胜率是轮走方对手的百分点，候选胜率为轮走方万分数，目差/ownership 为轮走方值；读取统一转黑方，写入反向转换。LZ2/LZOP2 是另一引擎槽，SGF 解析器只为这两项放行数字后缀，原文保留并校验，不与主槽混用。
- 坏 LZ 只在既有 `DocumentWarning` 中记录该节点/属性的 `InvalidValue { fallback: "ignored" }`，不阻止打开；非法着手节点不建立分析。`to_sgf_with_analysis(&BTreeMap<NodeId, SavedAnalysis>)` 在独立导出树保留未变化且仍有效的文件分析原属性（含顺序、扩展和格式），清除其余可解析旧主槽，仅为调用方提供的新有效结果写入主槽，保留损坏原文和第二槽；不改文档、撤销栈或 modified。候选胜率遵循 Java 的 1e-4 概率精度，writer 将超出 Java i32 范围的根 visits、候选 visits、edgeVisits 和 pvVisits 截为 2147483647，不改变内存结果；每个受影响节点返回一条 LZ / OutOfRange 警告。`to_sgf_with_analysis_and_warnings` 同时返回导出树与警告，AppCore 仅在写入成功后将警告附到 `DocumentChanged.warnings`（后续保存替换，内容编辑/换谱清除）；候选 order 仍独立验证，不视作计算量。`fixtures/lz/java-analysis.sgf` 是执行未修改 Java writer、注入说明中列出的合成数据产生的对照样本，不是真实引擎录制。
- AppCore 在换谱清理完成后、首次 `DocumentChanged` / Focus 前通过 `GameDocument::visit_saved_analysis` 读取主槽：先一次扫描属性标出 LZ/LZOP 及其祖先，仅回放这些路径，公共祖先只应用一次，单子链原地推进、分叉复制状态，没有主槽的文档不计算局面，无分析尾部和旁支不回放。沿途复用同一局面解析数据，不调用每节点 `position_at`；非法路径跳过后代、保留其他分支。导入及同谱恢复时已校验的节点同步标记图表有效性，首次发布不再次校验回放。随后转换为现有 `AnalysisResponse`，写入同一 `review.results: StoredAnalysis` 和 `summaries`。GraphView 从 summary 表读取；信息和候选点沿既有 `AnalysisUpdated` / `whole_game_result`；问题手、棋力评估沿既有保留结果表。因此没有引擎也可导航查看文件分析，不另建 UI 数据通路。`StoredAnalysis.saved` 是内部原始元数据，导出未被引擎替换的结果时保留 WRN/PDA 等字段；读取时仍检查 AnalysisKey，编辑失效、撤销可恢复。
- 文件来源发布为 `AnalysisSource::Saved`，不注入协调器 LRU/visits 下限；AppCore 对同 AnalysisKey 的文件结果保留显示深度，只有 root visits 严格更多的有效实时、整盘或持久缓存结果才能替换其候选点、来源和摘要。更浅和等深结果不会盖掉文件结果，缓存开关不影响该规则；同谱恢复引擎缓存后导入文件也按这一深度规则选择。整盘结果首次替换当前 Saved 时同步发布对应完整 Cache 视图，后续图更新保留这份焦点评价，不改变当前节点。每次 `DocumentChanged` 发布后重新发布当前有效的 Saved 焦点，保证自动曲线/缓存恢复更新图表、慢消费者的事件邮箱合并后，文档仍先于 Saved 到达；暂停切换清理未读分析后同样补发 Saved。引擎指纹变化只清引擎结果，尚未被替换的文件结果保留；换谱清命名空间。原文件不因为引擎重配被再次导入。ownership 长度与棋盘交叉点数不一致时只保留于文件元数据，不交给棋盘绘制。
- 旧 Leela LZ 可能完全没有目差：`AnalysisSummary.score_lead_available`、`CandidateView.score_lead_available` 和 `MoveLoss.score_loss_available` 为 false 时，其旧数值字段的 0 仅用于兼容，不能解释为已分析的平局/零损失；问题手评级以可用胜率计算、棋力评估按缺目差处理。Rust 始终返回标志，生成 TS 为可选属性，旧 mock 补 true；既有界面显示缺失目差提示需后续界面卡消费这些标志。
- 编码：BOM、`CA`、UTF-8、GB18030 / GBK（参考 Java 版 `EncodingDetector`）。
- P2-08 `sgf::parse_gib(bytes)` 使用现有严格解码顺序（BOM → UTF-8 → 声明 → GB18030），不统计猜测未声明的 EUC-KR；有歧义的旧韩文文件需先转为 UTF-8。UTF-8/GB18030 手写 golden 样本各有相邻的一行来源说明。INI/STO/SKI、固定让子点位和 GONGJE 按 Java `GIBParser`；让子以根 AB/HA/PL 表示，不计为普通着手。Java 未读取的段位、结果、日期仅补读取明确的标准字段：名字末尾括号段位、GAMEINFOMAIN 的 GRLT/ZIPSU、GAMETAG 的 C/W/Z/G（参照 Sabaki GIB parser），不推测自由文本。错误坐标/损坏着手拒绝导入，不悄悄漏手。
- GIB 的打开、对话框过滤器、原生拖入和系统打开共用同一导入事务；成功打开保留 basename 和最近文件，但 `DocumentView.file_path=null`，让现有 Save 首次选择 SGF 目标。后端拒绝任何 `.gib` 保存目标，原 GIB 不会被 SGF 覆写。
- Tauri `system_open` 在插件初始化前建立有序打开队列，统一接收启动参数、macOS `RunEvent::Opened` 的本地 file URL、main 窗口原生拖放，以及 Windows/Linux `tauri-plugin-single-instance` 回调。队列最终只调用 `AppCore::open_dropped_paths`，失败沿 `OpenFailed`，不创建第二套解析。二次启动的相对路径按发送方 cwd 解析，不采用第二次启动的配置目录；插件回调的 argv 为 UTF-8 String，首进程启动参数仍为原生 OsString。启动/Opened/二次启动在 Tauri 层行为测试中实际打开临时棋谱并核对失败事件；macOS Finder/Dock/open -a 和各平台安装后双击仍需真机验收。
- `tauri.conf.json` 登记 SGF Editor、GIB Viewer 文件关联与 MIME；Linux 包将扩展名 MIME 定义安装到 share/mime/packages。AppImage 的桌面入口注册由桌面集成器/用户完成；配置声明与 Rust 测试不能代替桌面环境的安装关联验收。
- P2-11 Java 导入使用显式包含 `config.txt` 的目录，另只读可选 `persist`；不自动搜全盘、不执行源命令、不写 Java 文件。`preview_java_import` 返回 actor 持有的预览 ID、原目录、含来源索引/缺失路径诊断的引擎项、Java 主引擎 ID、完整合并候选设置及问题列表，预览不创建新版设置。`confirm_java_import` 仅接受 ID，要求新版 Settings 与预览基线一致，然后原子保存；失败保留原设置，可重试，新预览取代旧预览。源目录与目标配置目录相同或目标位于源目录内（含符号链接）时拒绝。
- 导入同时识别 `leelaz.engine-command` / `engine-command-list` / `engine-name-list` 的旧格式及 `engine-settings-list` 对象格式，保留名字、程序、模型、配置、额外参数和问题；相对文件路径按 Java 目录解析，缺失路径仍保留。新增引擎追加到现有列表；已有主引擎保留，原无主引擎时保存 Java 选择但保持关闭，显式选择/重启命令才运行程序。Java 规则、读取贴目、默认贴目、活性检测、本地刷新间隔及已有 DisplaySettings 对应项合并，未出现的字段保留新版偏好。预览/确认接口为后续首次启动界面提供后端能力，本卡不接首次启动提示。手写样本和一行来源位于 `fixtures/java-config/`，不是用户真实配置。
- 应用标识 `io.github.wimi321.lizzieyzy.next2`，配置目录独立，可与 Java 版同时安装。

### P1 预览打包

- Open Sans 字体的 Apache License 2.0 全文逐字节保存于 `resources/licenses/OpenSans-LICENSE.txt`，固定大小和 SHA-256 放在 `scripts/packaging/bundle.py::APP_LICENSES`；四平台均沿现有许可证校验/复制流程打入 `resource_dir/licenses/OpenSans-LICENSE.txt`，资源清单记录哈希，验包要求该条目。字体资产由 P1-41 管理。
- `.github/workflows/preview.yml` 通过 `workflow_dispatch` 手动触发，也提供 `workflow_call` 供正式发布流程复用相同的下载、构建和验包步骤；后者以 `artifact_prefix`、`retention_days` 控制产物。使用冻结的依赖锁文件。Windows 生成 NSIS、macOS 生成 DMG、Linux 生成 AppImage 和 deb，artifact 名含平台、架构与运行 ID。Windows/Linux 预览使用 `--no-sign`；macOS 使用 `signingIdentity: "-"` 对应用 ad-hoc 签名，不使用发布者证书；桌面 crate 仍以 `--no-default-features` 排除开发工具二进制，Tauri 自身照常启用 `custom-protocol`。
- P1-34 的 `scripts/packaging/bundle.py prepare --platform <平台>` 从现有 `katago-assets.json` 读取固定引擎发布仓库、标签、归档 SHA-256/大小及默认 B11 的 URL、SHA-256/大小，不查询 latest 或静默换源。与 Java 主安装包一致：Windows/Linux 选 `windows-cpu` / `linux-cpu`（Eigen），macOS 选对应架构的 Metal 资产；安装路径分别为 `engines/katago/{windows-x64,linux-x64,macos-arm64,macos-amd64}/`，模型为 `weights/default.bin.gz`。整个引擎归档目录保留动态库、许可证和来源清单；Windows CPU 来源构建将运行库静态链接，不添加 CUDA/TensorRT 或依赖本机 GPU。
- 打包资源下载发生在打包准备步骤，存入 `target/packaging-cache/<sha256>`，每次缓存命中仍检查大小和 SHA-256；下载不完整或校验不符立即失败。归档拒绝路径穿越、链接和重名覆盖，成功后才发布 `target/bundled-resources`。CI 按平台、目录及打包脚本哈希缓存原始下载，不缓存已经签名的暂存目录。下载、模型和安装包均不入库；运行时用户显式下载另走 P2-12 的应用数据目录与下载 actor。
- `tauri.bundled.conf.json` 是打包时显式传入的资源映射，将 `target/bundled-resources/` 的内容直接映射到 Tauri `resource_dir`；默认配置仍携带 `katago/analysis.cfg`。普通开发、单元测试和 `verify.sh` 不要求下载大模型。正式构建也必须先执行 prepare 再使用该配置，不把下载或测试入口放入生产应用。
- macOS 捆绑配置的最低系统版本为 15.0，与固定引擎来源构建一致；在准备阶段对归档内 Mach-O 动态库及 katago 逐个 ad-hoc 签名、验证签名和库引用，拒绝 Homebrew 等外部路径；签名后生成 `bundle-manifest.json` 的逐文件 SHA-256、大小及可执行位。因此归档/原始引擎的来源哈希与签名后的安装文件哈希分开校验。解开 DMG 后再次核对逐文件哈希、签名并运行 `katago version`；干净环境的完整 Metal 分析仍须维护者手动验收。
- Windows readboard 固定为 `qiyi71w/readboard` v3.2.0（`readboard-webview2-v3.2.0.zip`，源码提交 b82039d），与 P1-33 协议实现参照的提交 a292eea 只差 3 个界面提交；钉选信息存于 `resources/katago/bundle-pins.json`。完整工具目录位于 `readboard/`，供 P1-33 在 `<resource_dir>/readboard/readboard.exe` 查找。v3.2.0 自身清单为 `asInvoker`，exe 原样打包；`elevationPatch` 为真时（旧版）才做 Java 的同长度 `requireAdministrator` → `asInvoker` 替换并记录前后哈希。上游归档内第三方许可证全部保留；readboard 经作者同意随新版分发，来源说明由 `resources/licenses/` 校验后打包。
- `scripts/packaging/acceptance.py` 实际解包 DMG/AppImage/deb 或静默安装 NSIS，逐文件对比暂存清单，检查安装路径、权限、安装包大小及 SHA-256。Windows/Linux 的 `smoke.py` 使用生产应用、全新 `--config-dir` 和真实捆绑 CPU/B11，通过原生 WebDriver 检查无设置窗口、保存的引擎/模型路径和 B11 规范名称、Ready 及当前棋盘的非零分析 visits；不注入假后端、不预填引擎配置。Windows 调试策略只由 CI 的 `smoke-windows.ps1` 临时设置，finally 和 always 步骤恢复。引擎/分析单元测试仍只用 fake-katago，离线打包脚本测试只用微型归档。所有产物校验结果、失败日志、下载/构建/总耗时写入 `target/` 或 CI artifacts/step summary，不提交证据文件。

### P2 发布打包（P2-15）

- `.github/workflows/release.yml` 接收 `v<SemVer>` 标签推送或手动触发，调用同一 `preview.yml` 下载、构建、验包和 Windows/Linux 干净配置 smoke。正式矩阵为 Windows x64 NSIS + portable ZIP、macOS 15 ARM64 / Intel 各一份 DMG 和更新用 `.app.tar.gz`、Ubuntu 24.04 x64 AppImage + deb。预览手动入口仍使用原来的三个 runner、未签名 Windows/Linux 和 macOS ad-hoc，不读取发布凭据；`ci.yml` 不变。发布流程不另跑 Rust 测试，Rust 验收仍由现有 CI 执行（Windows 保持 `RUST_TEST_THREADS=2`）。
- 手动输入 `tag` 可为空：此时从源码版本生成 `v<主.次.补丁>-preview.<run_id>.<run_attempt>`，可直接在无 secrets 的分支验证。标签版本经 SemVer / Windows 数值范围校验后，仅写入 `target/release-version.json`，作为 Tauri 构建配置覆盖；不改 Cargo/package.json 或工作区版本文件。指定已有标签时，草稿上传前要求该标签（含 annotated tag）解析到本次构建的精确提交，避免给旧标签挂新代码。
- 原生证书组不完整时明确跳过发布者签名，继续产出预览包；macOS 保留必需的 ad-hoc 签名。有 Developer ID 时先对捆绑 KataGo 和所有 Mach-O 库加硬化运行时、安全时间戳并验证，再生成资源 SHA-256 清单；Windows 对捆绑 exe/dll（包括 readboard）签名并验证后生成清单。Tauri 随后签应用、NSIS（含卸载器）或 DMG，不另行重签已通过验证的资源。没有额外 entitlements，保留最小权限。
- macOS 公证凭据齐全且证书已导入时，由 Tauri 使用 `notarytool` 公证并 staple app，之后才封装 DMG；后置 helper 验证 app 票据，再对 DMG 公证、staple、验证。缺公证凭据时保留已签名但未公证的包，并明确记录。空或部分 Apple 环境变量会在构建包装器中真正移除，避免 Tauri 把空字符串当成凭据。配置齐全但导入、签名、公证或验证失败时流程失败，不悄悄降级。
- `native_signing.py setup/build/notarize/cleanup` 管理临时 keychain / Windows 当前用户证书存储；P12/PFX 导入后立即删除临时文件，密码不写入配置、状态或 `GITHUB_ENV`，always 步骤恢复原 keychain 列表并移除本次导入的证书和私钥。上传仅白名单安装资产与诊断文件，不上传签名状态目录。`bundle.py prepare --release-signing` 是显式发布选项，未指定时沿用原行为。
- `release_assets.py collect` 从验包后的安装目录生成 portable ZIP / macOS 更新归档，再核对资源和安装包哈希；Windows ZIP 排除卸载器，保留已安装的主程序及全部资源。便携版指免安装解压运行，配置仍使用正常应用数据目录；WebView2 Runtime 仍需系统提供。macOS tar 保留 app 布局、权限和内部 framework 链接。Linux 继续直接使用通过原验包流程的 AppImage/deb。
- 聚合 job 只接受四个平台的完整八个资产，统一名称含版本、平台和架构。在所有原生签名、公证及 staple 完成后，用锁定的 Tauri CLI `signer sign --app-version <版本>` 给八个文件各生成 `.sig`；有公钥时再以 Node 内置 Ed25519 验证实际字节、可信注释和公私钥匹配。`latest.json` 含 version、notes、RFC3339 pub_date 和 URL/signature/sha256；平台键包含 Windows NSIS、macOS app、Linux AppImage/deb 的 bundle 类型键及四个兼容回退键。已锁定的 updater 2.14.1 支持 deb 按类型安装，因此 deb 不会收到 AppImage。所有可更新文件强制不超过 P2-14 的 1 GiB 上限。`SHA256SUMS` 总会生成；有签名时也覆盖 `.sig` 和 `latest.json`。
- updater 私钥或非空密码缺失时跳过全部更新签名和 `latest.json`，继续上传安装包及 SHA256SUMS；公钥缺失时日志明确写「本次构建的程序不会检查更新」，即使独立的签名组齐全仍可为既有客户端生成签名。公钥只通过构建环境嵌入，`tauri.conf.json` 的空 `pubkey` 保持不变。
- 只创建 GitHub Release **草稿**，权限仅聚合上传 job 为 `contents: write`。允许重跑更新同一提交的草稿；已发布 release、提交不一致或草稿多出旧资产（例如此前有 latest.json、本次缺私钥）均拒绝修改，交维护者审查。不会自动公开、自动删除旧资产或推送本地 git。发布说明可由手动 `notes` 输入，空时用版本和提交说明；若维护者修改说明，需要同时更新清单中的 notes。含预发布版本的草稿默认 prerelease；固定 `/releases/latest/download/latest.json` 不会跟随 GitHub prerelease，只有维护者发布可成为 latest 的正式 release 后才能完整验收自动更新。

| `APPLE_CERTIFICATE_PASSWORD` | 导出上述 `.p12` 时设置的非空密码原文 | 同上 |
| `APPLE_SIGNING_IDENTITY` | `security find-identity -v -p codesigning` 输出中的完整 `Developer ID Application: 姓名 (TEAMID)` 身份文本 | 同上 |
| `APPLE_ID` | 有权公证该应用的 Apple Developer 账号邮箱 | macOS 有证书则仍签名，跳过公证/staple |
| `APPLE_PASSWORD` | 在 account.apple.com 创建的 app-specific password，非 Apple 登录密码 | 同上 |
| `APPLE_TEAM_ID` | Apple Developer Membership 中的 Team ID 原文 | 同上 |
| `WINDOWS_CERTIFICATE` | 代码签名 CA 颁发且包含私钥的带密码 `.pfx` / `.p12` 的 base64 文本；PowerShell 可用 `[Convert]::ToBase64String([IO.File]::ReadAllBytes('codesign.pfx'))` | Windows 跳过 Authenticode，仍产出 NSIS 和 ZIP |
| `WINDOWS_CERTIFICATE_PASSWORD` | 上述 PFX 的非空密码原文 | 同上 |
| `GITHUB_TOKEN` | GitHub 自动提供，工作流以 `github.token` 使用；无需手工创建或保存 PAT，仓库策略须允许该 job 的 `contents: write` | 写权限被策略禁用时无法创建草稿，已构建安装包仍在 Actions artifacts |

Windows 当前实现接受可导出的 PFX；硬件令牌/HSM/云签名服务不在本卡范围，只有这些证书时保守留空，不伪造软件私钥。代码签名证书和 updater 密钥用途不同，不能互换。Apple 生成/导出步骤参见 [Tauri macOS 签名文档](https://v2.tauri.app/distribute/sign/macos/)，updater 密钥参见 [Tauri updater 文档](https://v2.tauri.app/plugin/updater/)。

维护者本地验证签过名的最终包（下面占位文件替换为实际路径，使用可信的公钥）：

```sh
export PATH="$HOME/.cargo/bin:$PATH"
# Linux 用 sha256sum -c SHA256SUMS；macOS 用 shasum -a 256 -c SHA256SUMS。
shasum -a 256 -c SHA256SUMS
# LIZZIE_UPDATER_PUBKEY 已设置为 .pub 的完整文本，不需要私钥。
node scripts/packaging/verify_release_signature.mjs '<asset>' '<asset>.sig' '<裸版本>'
# macOS 挂载 DMG 后验证里面的 app，以及下载的 DMG 自身。
codesign --verify --deep --strict --verbose=2 '/Volumes/<卷>/LizzieYzy Next 2.app'
codesign -dv --verbose=4 '/Volumes/<卷>/LizzieYzy Next 2.app'
spctl --assess --type execute --verbose=2 '/Volumes/<卷>/LizzieYzy Next 2.app'
xcrun stapler validate '/Volumes/<卷>/LizzieYzy Next 2.app'
codesign --verify --strict '<installer>.dmg'
xcrun stapler validate '<installer>.dmg'
```

Windows PowerShell 使用 `Get-AuthenticodeSignature '<installer>.exe'` 和 `signtool verify /pa /all '<installer>.exe'`，再对安装后/ZIP 内的主 exe、KataGo、readboard 及 DLL 执行同样检查。核对期望签发者，不能只看文件存在。新配置目录启动、真实 CPU/Metal 分析、文件关联、保留旧设置、完整下载更新到新版本及重启，仍需维护者在各平台验收。无 secrets 的四 runner 手动构建、完整 secrets 的签名/公证与草稿资产上传必须在 GitHub 上实际触发；本地 `actionlint` 和 `python3 -m unittest discover -s scripts/packaging -p 'test_*.py' -v` 只证明语法与脚本行为，测试签名密钥在临时目录随机生成并清理，不声称真实证书或安装器已验收。
